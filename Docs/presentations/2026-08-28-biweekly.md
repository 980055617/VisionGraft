## 1. Human — 配置とサイズ

### 症状: モデルが bbox を最大 2.27 倍はみ出す

原因は深度ではなく、**姿勢で bbox が縮むこと**だった。スケールは shot 先頭で固定するのに、
`bboxH` は姿勢で 441 → 130 と 3.4 倍変動する。深度は全編 0.72〜0.90m しか動いていない。

### 対処 ⑧: 投影骨高から深度を逆算する（`RefineDepthFromProjectedBones`）

ロック済みのスケールは動かさず、「投影された骨格高が bbox 高に一致する」深度へモデルを毎フレーム動かす。

| | OFF | **ON** |
|---|---|---|
| `boneRatio` median | 1.082 | **0.998** |
| max | 2.269 | **1.698** |
| 1.3 超のフレーム | 8.8% | **2.0%** |
| 球が人より手前 | 79.0% | **87.7%** |

胸トラップ区間（4-6s）の median が 1.522 → 1.110 と最も改善。**実機で大幅な改善を確認。**

派生して 2 件:

- **深度の揺れを潰した** — ⑧ は `bboxH` から深度を作るので検出ノイズが直接入り、1 フレームで最大 433mm 動いた。
  深度そのものではなく**補正比**を時定数 1.2 秒で平滑化し、被写体の実際の動きは残してノイズだけ取った（1f 変化 p90 5.0mm）
- **スクリーンを背景描画にした** — ⑧ で深度レンジが広がり 8.1% のフレームが `screenDistanceMeters` を越え、
  不透明なスクリーンにモデルが隠れて消えていた。スクリーンは遮蔽物ではなく背景なので
  Background キュー・`ZWrite Off`・`ZTest Always` に変更

### 対処 ⑨: 「人の位置」を Root から Hips へ（8/26）

「球が常に人より手前に見える」原因は、**モデルの `transform.position` が体の外にある**ことだった
（FBX の bind pose に焼き込まれたオフセット）。深度差を追う処理が、人の中にすらない点を人の位置として使っていた。

| 参照点 | 球表面→最近傍ボーン | 隙間が球の直径以内 |
|---|---|---|
| Root（従来） | 155.2mm | 1.0% |
| **Hips（採用）** | **22.1mm** | **79.8%** |
| MeshFront（事前の本命） | 88.8mm | 7.0% |

**「`anchor_z` は可視表面の depth だから MeshFront のはず」という事前の読みは外れた。**
理屈で決めていたら 88.8mm で止まっていた。

空中区間（蹴り上げ 9-12s）は 81.3mm と離れたままで、**一律に近づけているのではない**ことも確認した
（接触判定もしきい値も入れていない）。副作用で球が小さく写るようになったので深度に合わせてスケールも
追従させ、投影半径 / bbox 半径が **0.820 → 1.001**。実機で「だいぶ良くなった」。

**確定した教訓**: `instance.transform.position` は「人がいる場所」ではない。

## 2. Human — 姿勢一致

### 発端: 「実モデルが keypoint ほど曲がっていないのでは」という指摘

実ボーンと keypoints3d の投影位置の差（`[BONEKP]`）を初めて直接測ったところ、**基準点の取り違えが 2 件**見つかった。

| # | 取り違え |
|---|---|
| 測定側 | Unity の Foot ボーンを keypoints の Ankle と比較していた。Foot は実際には **Heel** の位置 |
| コード側 | `sourceShin` が「膝→足首」、モデル側が「膝→踵」で、**別区間で骨長比を計算**していた |

### 結果: 骨長補正を切ると足・手首がほぼ完全一致

| 部位 | 補正 ON | **補正 OFF** |
|---|---|---|
| 右足 | +17.5px | **0.0px** |
| 左足 | +11.2px | **−1.9px** |
| 右手首 | −5.7px | **−0.6px** |
| 右膝 | +3.7px | +10.3px ← 膝だけ ON が良い |
| RMS median | 6.35% | **5.85%** |

**「膝を 10px 合わせるために足を 17px・手首を 8px ずらす」割の合わないトレードオフ**だった。
`enableHumanBoneLengthCorrection` を**既定 OFF**（実機確認済み）。

2026-08-06 当時の前提（足首が bbox 高さの 10% 上にずれる）は ⑧ と bundle 側の depth 修正で既に成立しておらず、
**補正だけが当時の前提のまま残っていた。**

### AimAt は必須と再確認

| 設定 | RMS median |
|---|---|
| **AimAt ON / 骨長 OFF（現在）** | **5.85%** |
| AimAt ON / 骨長 ON | 6.35% |
| AimAt OFF | **24.79%** |

**切ると 4 倍悪化**（肘 +22〜25px 下、手首 −50〜60px 上）。FK だけでは四肢が keypoints の形にならない。

## 4. Animal — 姿勢一致（今回が初測定）

### 指標を作ったら、指標が乗っている前提が未検証だった

`[ANIMALKP]` を作って測ったが、**AniMer 26 関節と Unity ボーンの対応づけ自体が一度も検証されていない**ことに
気付いた。セグメント長比で照合したら対応づけが検証に落ちたので撤回し、bundle 側に対応表を依頼した（D-007）。

回答は **SMAL rest pose での最近傍マッチングによる実測**で届き、こちらで独立検証（左右を入れ替えた対立候補との
長さ比較 10/10、前肢の 1:2 長さ比）を通して受け入れた。**D-007 は解決。**

併せて、bundle 側が posed mesh 由来の keypoint が配布物の `keypoints3d` と 12 フレーム全部で小数 2 桁まで
一致することを確認しており、**入力に姿勢情報の欠落は無い**ことが確定した。

### 測ってみた結果: 全四肢が一様に 28〜50°

| 部位 | Dog | Lynx |
|---|---|---|
| 前肢 Upper | 17 / 15° | 26 / 37° |
| 前肢 Lower | 33 / 29° | 31 / 50° |
| 後肢 Upper | 40 / 36° | 30 / 28° |
| 後肢 Lower | 32 / 41° | 41 / 47° |

**単一の犯人はいない。** 一度「後肢 Upper が犯人（73〜79°）」と見えたが、これは
**起点の食い違い（kp7 は尾の付け根で股関節ではない、22° の系統誤差）が作った指標の下駄**だった。

### 重要な発見: 姿勢の「予算」は 13〜15° しかない

body frame で各ボーンの posed 方向と rest 方向のなす角を測った。

| | median | p90 |
|---|---|---|
| Dog 四肢計 | **15.3°** | 38.9° |
| Lynx 四肢計 | **12.7°** | 29.2° |

**動物の四肢は自分の rest 姿勢から 13〜15° しか離れていない。**
これが「姿勢を完璧に適用したときに得られる利益の全額」で、実測 30〜34° との差は
**リグの bind pose と SMAL rest skeleton の違い**に由来する。

ただしこれは「52 体のリグを作り直す」話ではない。現状のコードは姿勢のベースラインに
**リグの bind pose を焼き込んでいる**ので、これを SMAL の posed 方向に置き換えれば
コード 1 箇所で消せる可能性がある（未検証）。

### Animal AimAt（実装済み・実機確認待ち）

**第 1 版は失敗した。** keypoint の絶対位置に向けたところ脚が開き前脚が縮んで破綻。
原因は**スケールが 2 倍違う**こと — 表示モデルは高さ 0.42m のミニチュアだが、keypoint 骨格は実寸で体長 0.87m。

**第 2 版（2 つの keypoint の差 = セグメント向きを使う）で解消。** 差はスケール不変。
目視で破綻なし、当てていない部位への副作用 ±1°、肘 20〜29° / 膝 28〜52° で棒にも逆折れにもなっていない。
**後肢 Upper は AimAt から外した**（既知の 22° の下駄を入れるより現状の誤差を残すほうがよい）。

**ただし `video.mp4` は inpaint 済みで本物の動物が消えているため、この画像で正しさは確認できない。**
既定 OFF のまま、実機で元映像と重ねて確認するのが次。

### しっぽが動かない原因はコード側の減衰だった

## 5. Else（剛体）— 機関車が縦に立っていた

`bundle_train` で機関車が縦向きに立つ問題。**原因は prefab ではなく配置側**だった。

- prefab の root の X −90 度補正（長軸を横に倒す）は正しい
- `TrackPlacementWriter` が root の world 回転をまるごと書くので、補正が毎フレーム消える
- さらに生成時に回転を潰しているため、`ReplaceableModel.Awake` が**補正前の姿勢**で AABB を測り、
  高さ基準が屋根高 5.259m ではなく**車体長 18.507m** になっていた。**向きと寸法が同じ 1 つの原因から出ていた**

影響は全 75 モデル中 2 個だけ（実測）。うち `21_Donkey1.0` の root 回転は骨の位置から
**import 由来のゴミ**と判定（その回転はロバを尾で立たせる）し、コードに例外を書かず prefab を正規化した。

併せて、**`bundle_train` の track 0 は列車ではなく線路脇の信号柱**（22×132px で 61 秒間ほぼ不変）と判明。
横方向のフィットは、Animal で 8/07 に否定したのと同じ壊れ方（常に縮む・採用軸が入れ替わって不連続）を
train の実測でも再現したため**自動化しない**判断とし、手動倍率で合わせる方針にした。

### D-004 の顛末: `a`,`b` 較正 → 実距離配置 → 見送り

「Unity が `1/disparity` を距離とみなして配置している」ことが相対位置のずれの原因だと考え、
`disparity = a/Z + b` の較正値を bundle 側に依頼した。bundle 側は静止背景パッチ 2 点から shot ごとに解いて配布し、
こちらで独立に再現できた（誤差 median +9.7%、CV 0.090 が bundle 側の報告値 0.089 と一致）。

**しかし配置は変わらなかった。** 現行の popout 変換は配置直前に 2%/98% で正規化し直すため、
**`b` の効きが人−球の差で 2.19mm しか残らない**（完全な相殺ではない。一度「代数的に消える」と報告して訂正した）。
※ `b` が無意味なのではない。**実距離配置では同じ `b` が人の距離を 1.472m 動かす。** 桁が変換によって 3 桁違う。

そこで `a_metric = 3.507` をもらって実距離配置 `Z = a/((1−z01) − b)` そのものを比較した。

| 全編 2156f | 符号一致 | 相関 | 深度差の大きさ比（目標 1.0） |
|---|---|---|---|
| 現行 popout | 79.9% | +0.427 | **0.97** |
| 実距離配置 | 80.8% | +0.446 | **0.55** |

**順序は原理的に同じ**（どちらも `d` の単調関数）で、**差が出るのは深度差の大きさだけ。そこは現行が優る。**
本質は変換ではなく信号で、`anchor_z` と真の距離の相関が全編 +0.43 / 孤立フレーム +0.08 しかない。
**実距離配置は弱い信号を忠実に実距離へ写すので誤差も m スケールで出る。** 現行の圧縮レンジは誤差も圧縮している。

→ **実装見送りで両者合意。** `depth_scale_calibration` はコードに残すが既定 OFF。D-004 は「対応中」のまま
（閉じたのは `a,b` 較正というアプローチであって、根本原因は手つかず）。

### 副産物: ボールの bbox が約 5% 過大

こちらの独立推定と bundle の bbox が食い違う件を報告したところ、bundle 側が Hough 円検出で実測し
**bbox が 4.8% 過大**と確認した。補正すると含意直径が 20.7cm → **19.7cm**（3 号球の規定上限 19.1cm に対し +3%）。

同時にこちらの訂正も 1 件: 「独立な 2 経路（接触幾何 21.2cm / 較正 20.7cm）が一致する」と報告したが、
**どちらも同じ bbox 過大バイアスを含んでいた**ので独立ではなかった。

## 8. 検証手法について（今回いちばん学びがあった部分）

**「試算では効くはず → 実装 → 実機で効かない」を 3 回繰り返した。**

| 回 | 誤りの所在 |
|---|---|
| 1 | 試算は keypoints ベース、実装は実ボーンベース |
| 2 | 同上 + ログが効果を測れない位置にあった |
| 3 | 正規化で `b` が吸収されることを見落としていた |

**共通する原因は「実装前に評価方法の妥当性を確かめていない」こと。**
→ 方針化: **実装前に、その効果を測る方法が実装と同じ前提に立っているかを先に確認する。**

さらに 8/25 には**測定ハーネス自体が壊れていた**ことが判明した。

- バッチ実行のガード条件にフラグが無く、**設定が黙って無視**され両 run とも既定値で走っていた
- Unity の起動が非同期で、スイープの 3 つが同時起動してプロジェクトロックを奪い合い、先行分はクラッシュしていた

→ 方針化: **A/B ではまず「その設定が適用されたログ」が出力に存在するか確認する。**
数値が一致したときは「効果がない」より先に「条件が変わっていない」を疑う。

この 2 週間で否定した手（すべて実測または数学的に）: affine 較正 / 実距離配置 / `screenDistanceMeters` の拡大 /
popout レンジの拡大 / 毎フレームのスケール補正 / 腕への骨長補正の拡張 / Else のめり込み押し出し /
既知サイズによる距離推定 / 幅の自動フィット。
