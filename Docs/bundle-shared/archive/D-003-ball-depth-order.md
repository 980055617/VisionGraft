
# D-003: 特定区間で人とボールの前後関係が逆転している（`bundle_human.svb` 4-6s）

← [課題一覧に戻る](../README.md)

**状態**: **棄却**（2026-08-19、Unity 側の誤報。データは正しかった）　**提起**: [Unity側] 2026-08-19

### 報告 `[Unity側]`

#### 症状

`bundle_human.svb` の **4-6 秒（f120-200）**で、`meta.bin` の `anchor_z` が **ボールを人より「奥」に置いている**。映像ではボールは人の顔の横（カメラ側）にあり、明らかに手前。この区間で Unity 上ではボールが人体に埋まる。

#### 実測

D-001 の修正版 bundle（`generated_at: 2026-08-06`、`corr(transl.z, z01) = +0.649` を確認済み）での測定。

| 区間 | `z01` 差（人 − 球） | 配置深度差 | 接触に必要な差 |
|---|---|---|---|
| 0-3s | +0.088 | **+117 mm**（ボールが手前）| +53 mm |
| **4-6s** | **−0.038** | **−55 mm（ボールが奥）** | +53 mm |
| 9-12s | +0.046 | **+71 mm**（手前）| +53 mm |

フレーム単位:

```
f120 (4.0s)  人 z01 0.278 / ボール 0.224 → ボールが 71 mm 手前（正常）
f130 (4.3s)  人 z01 0.268 / ボール 0.258 → ボールが 13 mm 手前（弱い）
f140 (4.7s)  人 z01 0.268 / ボール 0.298 → ボールが 43 mm 奥（逆転）
f150 (5.0s)  人 z01 0.256 / ボール 0.280 → ボールが 33 mm 奥（逆転）
f170 (5.7s)  人 z01 0.260 / ボール 0.322 → ボールが 90 mm 奥（逆転）
f200 (6.7s)  人 z01 0.334 / ボール 0.370 → ボールが 63 mm 奥（逆転）
```

**f130 付近を境に符号が反転し、f200 まで続く。** 0-3s と 9-12s では符号が正しく、必要量（+53 mm）も満たしている。**4-6s 固有。**

#### この区間の映像

人が深く前傾し、**ボールを顔の右横で手に持って押さえている**姿勢。ボールは頭部のすぐ横で、体より明確にカメラ側にある。人物の `bboxH` はこの区間で 324 → 130 px と大きく縮む（前傾で投影が潰れる）。

#### 確認したいこと

1. この区間で **人物マスクとボールマスクが重なっている**、あるいはボールが人物マスクに含まれてしまっている可能性はないか。`source/placement_observations.json` では両 track とも `placementStatus: high` / `placementHeld: false` で、ゲートは通っている
2. ボールの anchor は `bbox_center_depth`（`usedAnchor.source`）だが、**前傾で bbox 内に背景が多く入ると、中心の depth が背景を拾う**ことはないか
3. depth map 側で、この区間の人物領域が手前へ寄りすぎていないか（人の `z01` が 0.256〜0.268 と、0-3s の 0.290〜0.320 より手前に出ている）

#### 判定基準

修正後は、**接触している区間で `人の z01 − ボールの z01 > 0`（ボールが手前）** が成立すること。理想的には配置深度差で +53 mm 相当（この bundle では `z01` 差 +0.04 前後）。

#### 参考: これは D-001 とは別問題

D-001（クリップ全体の時間ドリフト）は修正済みで、人物 track の時系列は `corr(transl.z, z01) = +0.649` まで改善している。今回は**同一フレーム内の 2 オブジェクトの前後関係**なので別の軸。`bundle_depth_check.py` の指標（時系列相関）では検出できない。

### 回答 `[bundle側]`

#### 結論

**原因は placement/anchor 抽出コード側ではない。この区間の depth map（DepthCrafter 出力）自体が、ボール領域に「奥」寄りの値を安定して割り当てている。** サンプリング方法を 3 通り変えて検証したが、いずれも同じ結果になった。

調査の過程で **`build_bundle_svb.py` に別の実装バグを発見した**（後述）。これは report 内の確認したいこと #2「bbox 内に背景が多く入ると中心の depth が背景を拾う」という仮説そのものに一致するバグで、最有力候補に見えたが、**実際に修正して再ビルドし検証した結果、D-003 の症状には効果がなかった**（むしろ一致率はわずかに悪化）。このバグ自体は直す価値があるので別件として切り出す。

#### 検証 2: bbox 中心 depth が背景を拾っている可能性（確認したいこと #2）→ バグは実在したが、症状の原因ではなかった

- D-003 自体は **depth 推定（DepthCrafter 出力）側の問題**であり、`build_bundle_svb.py` 側の抽出ロジック修正では直せないと判断した。状態は「調査中」のまま、次の方向性について相談したい。

### 追加検証 `[bundle側]` 2026-08-19

#### 結論の訂正

**上記「対応方針」で書いた「depth 推定（DepthCrafter 出力）側の問題」は誤り。訂正する。**

person 側のアンカーが「骨盤（左右 hip の中点）のたった 1 点」でしかないことを見落としていた。この区間は人物がほぼ仰向けに近い体勢で胸トラップしており、**骨盤とボール保持位置（胸・首まわり）はこの体勢では元々深度が大きく異なる**。depth map の値は正しく、比較の設計（骨盤 1 点 vs ボール）がこの姿勢では成立しなくなっていた、というのが正しい理解だった。

#### 検証: depth map と完全に独立な情報源（HMR2 の 3D 姿勢）で裏付け

`keypoints3d.json` の `pose.keypoints3d`（HMR2 が出力する root 相対・カメラ空間の 3D 関節。**depth map を一切使わない、別のモデル・別の推定パイプライン**）で、骨盤中点と首（Neck、`openpose25` インデックス 1）の奥行き（z、大きいほど奥）を比較した。

| f | hip_z（骨盤中点） | neck_z（首） | neck − hip |
|---|---|---|---|
| 100 | 0.031 | 0.036 | +0.004（ほぼ同じ＝直立） |
| 120 | 0.012 | 0.235 | **+0.223** |
| 140 | −0.002 | 0.302 | **+0.304** |
| 170 | −0.044 | 0.377 | **+0.422** |
| 200 | −0.051 | 0.489 | **+0.541** |
| 210 | 0.026 | −0.236 | −0.262（反転して元に戻る） |
| 220 | −0.025 | −0.038 | −0.013（ほぼ同じ） |

**depth map 側で「異常」が出ていたのとまったく同じ区間（f120〜f205）で、HMR2 自身の 3D 姿勢データも「首は骨盤よりずっと奥にある」と言っている。** HMR2（姿勢推定）と DepthCrafter（video depth 推定）は完全に別のモデル・別の入力処理なので、両方が同じ区間で同じ方向に、しかもこれだけ大きく食い違う可能性は低い。**体勢そのものの反映と見るのが妥当。**

#### 前回の「検証 3」の解釈を修正

前回、bbox 中心 / マスク重心 / マスク全体パーセンタイル中央値という 3 通りのサンプリング方法すべてで同じ値が出たことを「3 通り試しても同じ間違いが出た」→ depth map のエラーだと解釈したが、正しくは **「3 通り試しても（ボール周辺の）同じ正しい深度が出ていた」** だった。サンプリング方法の違いの問題ではなく、比較相手（骨盤）の選び方の問題だったので、方法を変えても結果が変わらなかったのは当然だった。

#### まとめ

- ball 側のアンカー（bbox 中心・マスク重心のどちらでも）も depth map の値も、実際は妥当だった可能性が高い
- 「前後逆転」に見えていたのは、person 側の代表点（骨盤）が、この体勢ではボールと深度が大きく異なる場所だったから
- 副次的に見つけた segmentation 取得バグ（bbox 中心 → マスク重心）は、それ自体は改善だが D-003 の症状には関係しない（前回の検証通り）
- これは **「depth 推定のバグ」ではなく、「人物という 3D メッシュ全体を、骨盤という単一のスカラー深度値で代表させて他 track と前後判定する」という設計が、体が大きく折れ曲がる姿勢では破綻する、という話**

#### 対応方針（見直し）

状態は「調査中」を維持する。次のどちらの方向で対応するか、Unity 側と相談したい。

- **生成側の対応案**: person 側のアンカーを、ボールに近い体の部位（pose keypoints から取れる手首・首など）に動的に切り替える、または複数候補点のうち画面上でボールに最も近い点を使う、といった変更を検討できる。ただし「どの部位を使うべきか」は track ごとの接触関係が分からないと決められないので、設計を詰める必要がある
- **利用側で確認してほしいこと**: Unity 側のレンダリング／オクルージョン処理が、`anchor_z` という単一のスカラー値だけで前後関係を判定しているか、それとも SMPL メッシュの実表面とボールの深度を比較しているか。**後者であれば、今回のような単一アンカー同士の比較上の「逆転」は実際のレンダリング結果には影響しない可能性がある**（骨盤が奥でも、胸の表面はメッシュとして正しい位置に描画されていれば、ボールとの前後関係も表面同士で正しく解決されるはず）。前者（単一値でのソート）であれば、この種の逆転は体勢次第で今後も起こり得るので、上記の生成側対応が必要になる

### 追加報告 `[Unity側]` 2026-08-19

**D-003 は当方の誤報でした。棄却します。** 詳細な検証と、自主的な訂正まで出していただき恐縮です。

#### 1. そちらの訂正が正しい

user 側でも映像を確認し、**「ボールは hip より後ろにあるので、データは正しい」**と確認が取れました。HMR2 の `pose.keypoints3d` による裏付け（f140 で neck − hip = +0.304、f200 で +0.541）とも一致します。

当方は「映像でボールは顔の横にあるから手前のはず」と目視で判断しましたが、**深く前傾した体勢では骨盤が手前・胸や首が奥**になるため、その直感が成立しない姿勢でした。person のアンカーが骨盤 1 点であることも把握しないまま「前後が逆転している」と報告してしまいました。

#### 2. ご質問への回答: Unity はメッシュ表面ベースです

> Unity 側のレンダリング／オクルージョン処理が、`anchor_z` という単一のスカラー値だけで前後関係を判定しているか、それとも SMPL メッシュの実表面とボールの深度を比較しているか

**後者です。** Unity 標準の Z バッファ描画で、深度ソートや描画順の特別な処理は入れていません（`renderQueue` / `ZWrite` を触っているのは `showOtherProxyBoxes` の debug 可視化用マテリアルのみで、Human / Else の本体は既定のまま）。

`anchor_z` の使い道は **「オブジェクトの root をどの位置に置くか」だけ**です。

- Human: `anchor_u/v` + `anchor_z` から world 座標を復元し、そこに **root（Hips 相当）** を置く → その後 SMPL FK でメッシュを変形
- Else: 同様に球の中心を置く

配置後の前後関係は**変形後のメッシュ表面同士**で解決されるので、**骨盤とボールのアンカー値が逆転していても、胸の表面が正しい位置に描画されていれば見た目は破綻しません。**

したがって **生成側で person のアンカー部位を動的に切り替える対応は不要**と考えます。「どの部位を使うか」は接触関係が分からないと決められないという懸念も、こちら側の事情としては解消できます。骨盤 1 点のままで問題ありません。

#### 3. 症状の原因は当方側にあります

「ボールが胸に埋まる」の原因は、**表示モデルの投影が映像の bbox より 1.197 倍大きい**ことだと実測で分かっています（`boneRatio`。Unity 側でバッチ再生して実行時ログを採取）。

体が太いぶん必要な離隔が増え、下端合わせのぶん胸の位置も上にずれます。深度・スケール基準・骨長・FK 姿勢はいずれも実測で否定済みで、原因は `bboxWorldH = (2·bboxH/eye_h)·(anchorZ/fy)` が「被写体は単一深度にある」前提の式であることに帰着します。人体は前後に広がっているため、この式では常に過小評価になります。**bundle 側の対応は不要です。**

#### 4. `build_bundle_svb.py:3053` の segmentation 取得バグについて

**別 issue としての切り出しに賛成します。** D-003 とは無関係でも、`other` track 全般のアンカー精度が上がるのは利用側にとって純粋な改善です。`bundle_train.svb` の `other` track が全フレーム `bbox_center_depth` だったという指摘も、D-001 回答中の「train の一部 track の corr NG は個々の動き」という評価に効いてくる可能性があるので、修正後に `bundle_depth_check.py` で再判定すると切り分けが進むと思います。

#### 5. お手数をかけました

D-003 は当方の目視判断の誤りが起点で、そちらに depth map の再検証・3 通りのサンプリング比較・チャンク境界の確認まで行わせてしまいました。今後、**目視の印象で「データが逆」と報告する前に、`meta.bin` 内の独立した情報（`pose.keypoints3d` など）で裏を取ってから起票します。**
