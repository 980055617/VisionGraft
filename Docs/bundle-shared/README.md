# bundle 共有ノート（生成側 ⇄ 利用側）

`.svb` bundle を**作る側**（Python プロジェクト）と**使う側**（Unity / VisionGraft）で共有するノート。
両プロジェクトに**同じ内容**を置き、更新のたびに手でコピーして同期する。

## このフォルダの使い方

**この `bundle-shared/` フォルダごとコピーして相手に渡す。** 中のファイルは全部まとめて 1 セット。

```
docs/bundle-shared/
├─ README.md               ← このノート
└─ bundle_depth_check.py   ← 検証ツール（依存なし・単一ファイル）
```

1. **両方のリポジトリの同じ場所に、フォルダごと同じ内容で置く**（Unity 側: `docs/bundle-shared/`）
2. 片方で更新したら、**フォルダごとコピーして**もう片方に上書きする
3. 貼ったら「同期ログ」に 1 行足す。**これを忘れると、どちらが新しいか分からなくなる**
4. **追記のみ。既存の記述は消さない。** 状況が変わったらステータスを更新し、経緯は残す
5. 各記述の頭に `[Unity側]` / `[bundle側]` と日付を付ける

**衝突を避けるために**: 課題の詳細は「報告」欄と「回答」欄に分かれている。自分の側の欄だけに書けば、互いの更新が同じ行にぶつからない。相手の欄は空のまま残しておくこと。

もし両側が同時に編集してしまったら、**同期ログの最終行より後の追記だけ**を手で拾って混ぜる。

**ファイルを増やすとき**: このフォルダに入れて、上のツリーに 1 行足す。フォルダの外に置くと渡し漏れる。

## D-001: 1 shot の長尺クリップで `anchor_z` がドリフトする

**状態**: 対応中　**提起**: [Unity側] 2026-08-17

### 報告 `[Unity側]`

#### 要約

`bundle_human.svb` / `bundle_train.svb` で **`meta.bin` の `anchor_z` が被写体の距離を表していない**。
同じパイプラインで生成された `bundle_animal.svb` は正常なので、**原理的な限界ではなく特定条件で起きる不具合**。

条件は **shot 数**と対応している。

| bundle | shots | 長さ | 判定 | 判定に使った指標 |
|---|---|---|---|---|
| `bundle_animal.svb` | **15** | 71 s | **OK** | corr(SMAL `transl.z`, `z01`) = **+0.550 / +0.624** |
| `bundle_human.svb` | **1** | 72 s | **NG** | corr(SMPL `transl.z`, `z01`) = **+0.026** |
| `bundle_train.svb` | **1** | 61 s | **NG** | corr(bbox 径, `z01`) が全 8 track で**正**（負であるべき） |

2026-08-05 に対処された「チャンク間ドリフト」（全体 R² 0.0037 → 0.1657）の**残存**と考えている。R² 0.1657 は相関で言えば 0.41 でまだ足りない。カットが多い素材では shot 境界がドリフトの蓄積を実質的に断ち切るため露見せず、**1 shot の長尺クリップでのみ症状が出る**、という説明がすべての観測と整合する。

#### 利用側で起きること

`anchor_z` は popout レンジ（0.35 m）に写されてオブジェクトの配置深度になる。`bundle_human.svb` の実測:

- 立位（keypoint 身長 1.45–1.75 m）かつ `transl.z` がほぼ同じ = **人が同じ場所に立っている 386 フレーム**で、`z01` が **0.180〜0.398** に散る
- 配置深度に直すと **253 mm のばらつき**。表示身長 0.398 m の **64%**
- 人とボールの深度差は median 80 mm なので、**ばらつきが深度差の 3.8 倍**
- 人とボールの前後関係の一致率は **33%**（偶然の 50% より悪い）

見た目の症状は「胸トラップや足でボールを扱う場面で、ボールが人体に埋もれる」。

#### 根拠

**1. 距離を正しく捉えている系列が 2 つあり、互いに一致している**

`bundle_human.svb` の person track（1 秒 median に平滑化）で corr(SMPL `transl.z`, 1/`bboxH`) = **+0.691**。
`transl.z`（4D-Human の weak-perspective カメラ距離）と `bboxH`（検出 bbox 高さ）は**独立した推定**なので、一致していることは両方が距離を捉えている証拠。

**2. `anchor_z` だけが無相関**

| 検証 | 値 | あるべき値 |
|---|---|---|
| corr(`transl.z`, `z01`) | **+0.026** | +1 に近い |
| ↑ 立位フレームのみ | +0.078 | +1 に近い |
| corr(1/`bboxH`, `z01`) | −0.109 | +1 に近い |

**3. 同じ bundle のボールは正常**

corr(ボール bbox 径, ボールの `z01`) = **−0.456** ✓（実サイズ一定なので径 ∝ 1/距離、負相関が正しい）。
**同じ depth map から取っているのに person track だけが壊れている。**

**4. 狂い方は単調ドリフト**

| 検証 | 値 |
|---|---|
| corr(person `z01`, **経過時間**) | **+0.657** |
| corr(ball `z01`, 経過時間) | +0.415 |
| corr(person `z01`, ball `z01`) | **+0.679** |

1 秒 median の推移:

| 時刻 | `transl.z` | `bboxH` | `z01` |
|---|---|---|---|
| 0 s | 102.2 | 414 | **0.195** |
| 24 s | 129.5 | 198 | 0.365 |
| 48 s | 100.4 | 441 | **0.310** |
| 72 s | 79.8 | 305 | 0.282 |

**0 秒と 48 秒は `transl.z`（102.2 / 100.4）も `bboxH`（414 / 441）もほぼ同じ = 同じ距離に同じ姿勢で立っている。それなのに `z01` は 0.195 と 0.310。**

`bundle_train.svb` の track 0 はさらに露骨で、`z01` が 0.506 → 0.952 へ単調増加（corr(`z01`, 経過時間) = **+0.951**）。

**5. ドリフトはシーン内の全オブジェクトに共通**

corr(person `z01`, ball `z01`) = +0.679。人とボールが**一緒に流れている**。差分を取ると前後関係がかなり回復する。

| 前後関係の一致率 | |
|---|---|
| 生の `z01` | **33%** |
| 人の `z01` − ボールの `z01` | **74%** |

**同一フレーム内の相対順序としては情報が残っており、失われているのは絶対値のほう。** ドリフトが「フレームごとの共通オフセット」として乗っていることを裏づける。

#### 生成側の観測ログは正常と報告している

`source/placement_observations.json` の person track:

| 項目 | 値 |
|---|---|
| `placementConfidence` | median **1.0**、低信頼 0.0% |
| `placementStatus` | 全 2167 フレーム `high` |
| `placementHeld` | **0.0%** |
| anchor source | 全て `depth_sample` |
| bbox 内 depth の IQR | median 0.00195（有効サンプル 49） |

**観測ゲート・hold・信頼度のいずれも異常を検出していない。** anchor のサンプリングは想定どおり動いており、サンプリング元の depth 値そのものが時間方向に流れている、という切り分けになる。

#### 確認したいこと

1. `--depth-chunk-size` / overlap のチェーン式アフィン合わせは 2026-08-05 に見直されたが、**1 shot 60〜70 秒（1800〜2200 フレーム）の素材で蓄積誤差が残っていないか**
2. `bundle_animal.svb`（15 shot）が正常なのは、**shot 境界でアフィン合わせが実質リセットされているから**という理解で合っているか。もしそうなら、カットのない素材には別の基準点が要る
3. チャンク間のアフィン合わせを**チェーンではなく共通参照**に変えられないか。クリップ全体で 1 回 min-max 正規化する現在の方針（`global_minmax_pre_clip`）とは別に、チャンク間がチェーンになっている点が蓄積の原因に見える

#### 修正後の判定基準

優先順位のとおりに確認してほしい。

| 優先 | 指標 | 目標 | 対象 |
|---|---|---|---|
| 1 | corr(`transl.z`, `z01`) | **> 0.5** | SMPL/SMAL を持つ track |
| 2 | corr(bbox 径, `z01`) | **< −0.3** | 実サイズ一定の Else track |
| 3 | corr(`z01`, 経過時間) | 0 に近い | 参考値 |

**指標 3 は単独では判定に使えない。** 被写体が一方向へ動き続ける映像（電車が遠ざかる等）では大きくて当然なので、指標 1 や 2 が NG のときに「狂い方が単調ドリフトなのか」を見分けるために使う。

指標 1 を使う前に **corr(`transl.z`, 1/`bboxH`) > 0.5** を確認すること。ここが低い場合は `transl.z` 自体が信用できない（フレーム数不足・推定が不安定）ので基準にできない。旧 `bundle.svb`（289 フレーム = 10 秒）が該当する。

#### 再現手順

```
python bundle_depth_check.py path/to/bundle.svb [more.svb ...]
```

**このフォルダ内の `bundle_depth_check.py`**。標準ライブラリのみで動く単一ファイルなので、どちらの環境でもそのまま走る。`.svb` の `meta.bin` + `manifest.json` だけを読み、track ごとに上の 3 指標と 1 秒 median の推移を出す。判定の符号は bundle 世代（`depth_policy` の有無 = `larger = farther` / `nearer`）を吸収済み。

**このツールは必須ではない**（生成側は `meta.bin` を作っている当事者なので読むコードは持っているはず）。同梱している理由は、判定基準を文章で書くだけでは解釈がぶれるため。1 秒 median に平滑化するかどうか、立位で絞るかどうか、旧世代の符号をどちら向きに正規化するかで値が変わり（`bundle_human.svb` の指標 1 は絞り方で +0.026 / +0.078 と動く）、「こちらでは 0.5 を超えた」という食い違いが起きる。**自前で書き直しても構わないが、その場合は同じ数字が出ることを確認してほしい。**

なお**原因究明には向かない**。生成側は `depth.npz` の生値・チャンク境界・アフィン係数の履歴を見られるので、そちらのほうが直接的。これは `.svb` の出力だけを見る**最終成果物の検査ツール**。

### 回答 `[bundle側]`

#### 結論

**原因は特定できた。ただし「2026-08-05 のチャンク間ドリフト修正が不十分」ではない。修正自体は効いている。渡っていた `bundle_human.svb` / `bundle_train.svb` が、その修正より前に作った `depth.npz` のままビルドされていた、というだけ。** `bundle_depth_check.py` を使って手元で再現・検証済み。

`shared_volume/sam2_bundle_jobs/` を見ると、2026-08-05 にチャンク間アフィン合わせを「チェーン」から「全ペアの重なりを同時に解く joint least-squares」に変更する修正（`StereoCrafter/depth_splatting_inference.py` の `_solve_global_chunk_affine`、report 内の確認したいこと #3 そのもの）が入っており、`20260805-{human,train,animal}-depth-chunkfix/` という検証専用ジョブで `depth.npz` を再生成して `bundle.svb` を作り直し、効果を確認していた形跡がある。**しかしこの再生成された `depth.npz` は `FINNAL_HUMAN` / `FINNAL_TRAIN` の本番ディレクトリには一度もコピーされておらず、そこにある `depth.npz` は今も 2026-07-27（human）/ 2026-07-29（train）時点の、修正前のものだった。**

紛らわしい点として、`bundle_shots_depthfix.svb`（2026-08-06 生成）や `bundle_shots_h264fix.svb`（2026-08-07 生成）はファイル名だけ見ると「直っていそう」だが、中身の `depth.npz` は差し替わっていない。この2つの "fix" はどちらも別件（`depthfix` = anchor_z の符号規約統一、`h264fix` = Quest 向け H264 再エンコード）で、チャンクドリフト修正とは無関係。命名が衝突していて紛らわしかった。

#### 検証

`20260805-*-depth-chunkfix/` に残っていた再生成済み `depth.npz` を使い、現行の `build_bundle_svb.py`（2026-08-06 の anchor_z 規約修正込み）でビルドし直し、渡された `bundle_depth_check.py` で確認した。

| bundle | 指標 | 修正前（渡した版） | 修正後（`depth.npz` 差し替え） |
|---|---|---|---|
| human track0 (person) | corr(transl.z, z01) | **+0.010** NG | **+0.649** OK |
| human track0 | corr(z01, 経過時間) | ±0.68（単調） | -0.12 |
| train track0 | corr(z01, 経過時間) | **+0.951**（report記載の 0.506→0.952 そのもの） | **+0.33**、推移はほぼ平坦（0.79〜0.83） |
| animal | （参考） | OK | OK（変化なし） |

train は他の短尺 "other" track（8〜33秒しかない車両ごとの track）で corr(bbox径, z01) が一部まだ NG のままだが、この指標はツール自身のコメント通り「画面外への切れ・隠れに弱い参考値」で、かつ**全 track が揃って +0.9〜0.96 という「同じ方向に流れる」シグネチャ（report の根拠5と同じパターン）が、修正後は track ごとにバラバラで弱い値になった**。これは共通のドリフトではなく個々のオブジェクトの実際の動きと見るのが妥当。

検証に使ったビルドは上書き・削除せず、新規ジョブとして置いてある:
`shared_volume/sam2_bundle_jobs/20260817-d001-depth-drift-verify/`（`bundle_human.svb` / `bundle_train.svb` / `bundle_animal.svb` + `manifest_*_dump.json`）。**これは検証用の再ビルドであり、まだ正式な再配布物ではない**（Quest向け H264 再エンコードや `bundle_consistency.json` の全項目チェックをまだ通していない）。

#### 確認したいこと（report内の3項目）への回答

1. **残っていたか** → 残っていたが、原因は「合わせ方が甘い」ではなく「修正後の `depth.npz` が本番ディレクトリに配布されていなかった」。修正後の `depth.npz` を使えば 1800〜2200 フレームの単一 shot でも上の指標は通る。
2. **shot境界がチェーンを断ち切っているから animal だけ OK、という理解は合っているか** → **合っていない可能性が高い。** `scripts/run_sam2_to_bundle.py` を確認したところ、`shots.json` は inpaint 段と bundle 構築段にしか渡されておらず、DepthCrafter のチャンク分割・アフィン合わせ自体は shot 境界を一切見ていない（`depth_splatting_inference.py` 側に shots の概念がない）。つまり shot 数によってチャンク間ドリフトの蓄積量が変わる機構は今の実装には存在しない。animal が元々 OK だったのは、たまたま animal の該当区間の残差が小さかった／ノイズの範囲だっただけで、shot 境界のおかげではなさそう。

#### 2. ご質問への回答: Unity はメッシュ表面ベースです

> Unity 側のレンダリング／オクルージョン処理が、`anchor_z` という単一のスカラー値だけで前後関係を判定しているか、それとも SMPL メッシュの実表面とボールの深度を比較しているか

- Human: `anchor_u/v` + `anchor_z` から world 座標を復元し、そこに **root（Hips 相当）** を置く → その後 SMPL FK でメッシュを変形
- Else: 同様に球の中心を置く

配置後の前後関係は**変形後のメッシュ表面同士**で解決されるので、**骨盤とボールのアンカー値が逆転していても、胸の表面が正しい位置に描画されていれば見た目は破綻しません。**

「ボールが胸に埋まる」の原因は、**表示モデルの投影が映像の bbox より 1.197 倍大きい**ことだと実測で分かっています（`boneRatio`。Unity 側でバッチ再生して実行時ログを採取）。

体が太いぶん必要な離隔が増え、下端合わせのぶん胸の位置も上にずれます。深度・スケール基準・骨長・FK 姿勢はいずれも実測で否定済みで、原因は `bboxWorldH = (2·bboxH/eye_h)·(anchorZ/fy)` が「被写体は単一深度にある」前提の式であることに帰着します。人体は前後に広がっているため、この式では常に過小評価になります。**bundle 側の対応は不要です。**

#### 4. `build_bundle_svb.py:3053` の segmentation 取得バグについて

**別 issue としての切り出しに賛成します。** D-003 とは無関係でも、`other` track 全般のアンカー精度が上がるのは利用側にとって純粋な改善です。`bundle_train.svb` の `other` track が全フレーム `bbox_center_depth` だったという指摘も、D-001 回答中の「train の一部 track の corr NG は個々の動き」という評価に効いてくる可能性があるので、修正後に `bundle_depth_check.py` で再判定すると切り分けが進むと思います。

#### 5. お手数をかけました

D-003 は当方の目視判断の誤りが起点で、そちらに depth map の再検証・3 通りのサンプリング比較・チャンク境界の確認まで行わせてしまいました。今後、**目視の印象で「データが逆」と報告する前に、`meta.bin` 内の独立した情報（`pose.keypoints3d` など）で裏を取ってから起票します。**

## D-004: `anchor_z` が実距離をほとんど再現していない（全 bundle 共通）

**状態**: 回答待ち ／ **提起**: [Unity側] 2026-08-20 ／ **対象**: `bundle_human.svb` / `bundle_animal.svb` / `bundle_train.svb`（D-001 修正後のビルド）

### 症状

Unity 側は `meta.bin` の `anchor_z`（正規化 disparity）を `Z ∝ 1/disparity` と解釈して、オブジェクトを画面手前の popout レンジに配置している。この解釈で得た距離が、**幾何的に求めた実距離と系統的にずれる**。

結果として、同一フレーム内の 2 オブジェクト（人とボール）の前後関係とサイズ比が崩れ、モデルがボールを飲み込む・逆に浮きすぎる、という症状が出る。単一のスケール係数では両立できないことを実測で確認済み。

### 測定方法

**実距離の求め方（depth map を一切使わない）**

- `person` / `animal`: `meta.bin` の keypoints3d（root 相対・カメラ空間・実寸メートル、実寸であることは別途検証済み）を距離 Z で透視投影し、**その投影高が bbox 高と一致する Z** を二分探索で求める。カメラ内部パラメータは `manifest.json` の `fy_norm` / `eye_h` を使用
- `other`: keypoints がないため実サイズ不明。bbox 径の逆数を相対距離とした（**この推定は物体の回転・変形に弱い**ので、下表の `other` 側は上限値として読んでほしい）

**フィット**

`disparity = a/Z + b` を最小二乗でフィットし、決定係数を見た（DepthCrafter は affine-invariant なので、この形が成り立つのが前提）。

### 結果

| bundle | track | 手法 | 決定係数 | depth 由来の距離 ÷ 実距離（p10-p90 の比） |
|---|---|---|---|---|
| human | 0 person | keypoints | **0.143** | 1.22 倍 |
| human | 1 other（ボール） | bbox 径 | 0.533 | 1.22 倍 |
| animal | 0 animal | keypoints | **0.110** | **3.07 倍** |
| animal | 1 animal | keypoints | 0.330 | 1.36 倍 |
| train | 0 other | bbox 径 | **0.001** | 1.33 倍 |
| train | 1 other | bbox 径 | 0.360 | 7.52 倍 |
| train | 2 other | bbox 径 | 0.797 | 11.24 倍 |
| train | 3 other | bbox 径 | 0.546 | 16.13 倍 |
| train | 4 other | bbox 径 | 0.417 | 18.65 倍 |
| train | 5-7 other | bbox 径 | 0.002-0.040 | 5.7-8.2 倍 |

`bundle_human.svb` の詳細:

```
a = 0.6059   b = 0.5123   決定係数 = 0.143
disparity の実測レンジ : 0.544..0.822
うち a/Z が動かす分    : 0.100..0.249
b（距離に依らない定数）: 0.512
```

**もっとも信頼できるのは human の person（keypoints 由来・実寸検証済み）と human の other（剛体の球なので bbox 径が信頼できる）で、どちらも決定係数が低く、ばらつき 1.22 倍。** train の大きい値は bbox 径推定の弱さを含むので割り引いて見てほしいが、決定係数 0.001 / 0.002 / 0.028 / 0.040 という track が複数あるのは、推定手法の弱さだけでは説明しにくい。

### Unity 側で確認済みのこと（＝そちらに対応をお願いする理由）

- **`a`, `b` の較正では直せない。** Unity は最終的に disparity を popout レンジへ線形正規化して押し込むので、`Z = a/(disp − b)` の `a`（スケール）と `b`（シフト）は**正規化に吸収されて完全に消える**。実際に全編較正・3 秒ごとの区間別較正の両方を試算したが、`boneRatio` のばらつきは 1.22 倍のまま変わらなかった
- **実距離を直接使えば改善するが、汎用性がない。** keypoints 由来の実距離をそのまま使うと ばらつき 1.22 → 1.12 倍、問題区間の過大投影 1.391 → 1.166 に改善する。ただしこれは keypoints を持つ `person` / `animal` にしか使えず、**`bundle_train.svb` のように `other` のみで構成される bundle には原理的に適用できない**。また人だけ基準を変えると人と `other` で深度の基準がずれ、前後関係が壊れる
- D-001（クリップ全体の時間ドリフト）は修正済みで、これはその修正後のビルドでの測定。**別軸の問題**

### 確認・相談したいこと

1. **`manifest.json` に metric depth への変換係数（`a`, `b`）を載せられないか。** これは Unity 側の正規化を metric ベースに置き換える前提での依頼。ただし上記のとおり決定係数が低いので、係数を貰っても再現性が上がるとは限らない。**まず「そちらの手元で depth と実距離の一致度をどう評価しているか」を教えてほしい**
2. **DepthCrafter 出力の素の品質を、そちらの指標で確認してほしい。** 決定係数 0.143（human person）という値が、そちらの想定内なのか想定外なのか知りたい。想定内であれば、この精度を前提にした配置設計を Unity 側で組む
3. `other` track のアンカーが D-003 で見つかった segmentation バグの修正後どうなったか。今回の測定は `bundle_train.svb`（修正前のビルド）なので、修正後ビルドで再測定する価値があるか
4. animal track 0 の 3.07 倍が突出している。この track に固有の事情（オクルージョン・フレームアウト等）に心当たりがあるか

### 再現方法

`tools/bundle_depth_check.py` と同じ `Bundle` クラスで読める。測定スクリプトが必要であれば同梱するので言ってほしい。
