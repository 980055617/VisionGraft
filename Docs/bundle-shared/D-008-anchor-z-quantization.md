# D-008: 同一フレーム内で `anchor_z` が近接物体を分離できない（`bundle_train.svb`）

← [課題一覧に戻る](README.md)

### 症状（Unity 側の見え方）

列車が奥から一車両ずつ近づいてくる動画で、**最初の数秒だけ前後関係が逆になる。**
映像では track 1 が手前・track 2 が少し奥なのに、モデルを置くと 2 が手前に来る。

### 実測

`meta.bin` を runtime と同じ手順で読み、`PinholePlacementSpace` の式をそのまま移植して
3D 位置を出した。**再現コードをこのフォルダに入れてある**: `train_depth_order.py`。

```
python train_depth_order.py <bundle.svb> [フレーム番号...]
```


```
frame 160   track 1  anchorU=369  anchorZ=0.8460  camX=-0.2508  視点からの距離 0.8828
            track 2  anchorU=417  anchorZ=0.8480  camX=-0.2069  視点からの距離 0.8736
            track 3  anchorU=443  anchorZ=0.8480  camX=-0.1828  視点からの距離 0.8683
```

**車両どうしの `anchor_z` の差が 0.002 = `quant_pos_scale` の 1 段しかない。**

### 順序が間違っているのではなく、分解能が足りない

車両 track が 2 つ以上写る 324 フレームを数えた:

| 指標 | track 番号順に単調 |
|---|---|
| `anchor_z`（昇順＝遠ざかる） | **95%** |
| `anchor_v`（降順＝画面の上へ） | 93% |
| `bbox_h`（降順＝小さくなる） | 86% |
| `bbox_w`（降順） | 77% |

**`anchor_z` の順序自体は 95% 正しい。問題は 32% のフレームで車両どうしが同値になること。**

同値になると camZ が完全に一致し、映像に写っている前後関係が**配置にまったく反映されない**。
そのうえ pinhole 復元では `x = xNdc * z / fx` なので、camZ が同じなら視点からの距離は
横方向のずれで決まる。手前の車両ほど画面の左（＝光軸から遠い）にいるので、
**最も手前の車両が最も遠くに置かれる**。上の frame 160 がまさにその形。

各 track の `anchor_z` は時間方向には大きく動いている（track 1 は 0.636〜0.846）。
近づけば分離する。**遠方でだけ潰れている**ので、正規化深度の遠方飽和に見える。

| bundle | `anchor_z` の全体範囲 |
|---|---|
| `bundle_train.svb` | 0.596 〜 0.944 |
| `bundle_human.svb` | 0.128 〜 0.460 |
| `bundle_animal.svb` | 0.274 〜 0.746 |

### 聞きたいこと

1. `anchor_z` は何をサンプリングした値か。正規化深度（0..1）をそのまま入れているか、
   メートルへ直しているか。D-004 の続きとして知りたい
2. 遠方が飽和するのは depth モデルの性質か、正規化のかけ方か
3. `quant_pos_scale = 0.002` は近距離向けの刻み幅に見える。遠方で 1 段に潰れるなら、
   量子化の前に分離が失われているのか、量子化で失われているのかを切り分けたい
4. 同一フレーム内の相対順序だけでも保証できる余地はあるか
   （絶対距離が合っていなくても、前後関係が保てれば見た目は成立する）

### Unity 側で回避する場合の候補（未実装・要相談）

`anchor_z` が同値のときだけ `anchor_v`（93%）か `bbox_h`（86%）で順序を補う、という手はある。
ただし**新しい補正機構を足すことになる**ので、bundle 側で直せるならそちらを優先したい。

### 回答 `[bundle側]` 2026-09-04 — 主因は量子化。`quant_pos_scale` を 0.002 → 0.0001 にした検証ビルドを配布

先に結論を 3 つ。

1. **`anchor_z` は「正規化視差の反転値」そのもの**。`anchor_z = max(1 - disp_norm, 1e-4)` で、
   メートルでもなければ深度に比例してもいない。**視差に対して線形**なので、
   遠方が潰れるのは仕組み上の必然。manifest の `depth_policy.unrelated_to_anchor_z` に
   「anchor_z は depth_npz とは別の量」と書いてあったが**これが誤り**で、
   そちらが Q1 を聞かざるを得なかった原因。訂正した。
2. **潰れているのは主に量子化のせい。** 同一フレームのペア 3388 件のうち、
   **2.7% は量子化前から同値**（深度側の限界）だが、
   **36.0% は 0 でない差が `quant_pos_scale` より小さくて量子化で消えている。**
3. **`quant_pos_scale` を下げるだけで大半は戻る。** schema 変更なし、
   フィールド構成も変えていない。train の検証ビルドは 0.0001 で配布した
   （builder の既定値は 0.0002。理由は 4 に書いた）。

そのうえで、**そちらの再現スクリプトの判定基準（視点からのユークリッド距離）は
前後関係の指標としては使えない**、という指摘が 1 つある（3.5 に書いた）。

#### 0. どの bundle を測ったかの確認

そちらの表の `anchorU=369/417/443`・`anchor_z=0.8460/0.8480/0.8480` は
`FINNAL_TRAIN/bundle_shots_inpaintfix.svb`（D-002 で「推奨」とした版）と完全一致した。
以下すべてこのファイルでの実測。
`bundle_shots_depthdriftfix.svb` は `anchorU=372/418/444` で 3px ずれるので、
そちらが測ったのは inpaintfix 版で間違いない。

#### 1. `anchor_z` は何をサンプリングした値か

3 段でできている:

```
DepthCrafter → 視差（affine-invariant。disp_raw ≈ a/Z + b、a,b は未知）
             → クリップ全体の min-max 正規化 → depth_npz の disp_norm ∈ [0,1]
                                              （0.0 = 遠, 1.0 = 近）
             → アンカー画素まわり 7x7 窓の median を取る
             → anchor_z = max(1 - disp_norm, 1e-4)     ← これが meta.bin に入る値
```

- **メートルには直していない。** `a`, `b` が未知なので直せない（D-004/D-005 の結論のまま）。
- **深度にも比例していない。** `1 - disp_norm` は**視差の一次式**。
  `disp ≈ a/Z + b` なので `anchor_z ≈ const - a/Z` で、`Z → ∞` で有限値に収束する。
- 実装: `StereoCrafter/build_bundle_svb.py` の `disparity_to_camera_z()` と
  `sample_depth_median()`（窓サイズは `--sample_k`、既定 7）。

**manifest の記述を訂正した。** `depth_policy.unrelated_to_anchor_z`
（「anchor_z は depth_npz とは別の量なので near_far_direction を適用するな」）は
実装と食い違っていた。`relation_to_anchor_z` に差し替えて上の式を明記し、
あわせて `anchor_z_policy` ブロックを manifest に追加した。次回以降のビルドから入る。

#### 2. 遠方が飽和するのは depth モデルの性質か、正規化のかけ方か

**どちらでもなく、パラメータ化そのもの。** `anchor_z` が視差の一次式である以上、
`Z` の大きい領域は必ず潰れる。min-max 正規化はレンジの割り当てを変えるだけで、
潰れる順番は変えない。

そちらが出した 3 本のレンジがそのまま裏づけになっている:

| bundle | `anchor_z` の全体範囲（そちらの表） | 意味 |
|---|---|---|
| `bundle_train.svb` | 0.596 〜 0.944 | クリップ全体が視差 0.06〜0.40 の**遠方側**に乗っている |
| `bundle_animal.svb` | 0.274 〜 0.746 | 中間 |
| `bundle_human.svb` | 0.128 〜 0.460 | 近距離側 |

**train だけが壊れるのは、train だけがレンジの遠方端に丸ごと乗っているから。**
そちらの「遠方飽和に見える」という読みはそのとおり。

#### 3. 量子化の前で失われているのか、量子化で失われているのか

配布 bundle の `source/placement_observations.json` には、量子化前の
`usedAnchor.z`（builder が `anchor_z_q` にする直前の float）が入っている。
まずこれが本当にこの bundle の元データかを確認した:

```
5995 オブジェクト全部で quantize(usedAnchor.z, 0.002) == meta.bin の anchor_z_q
→ 不一致 0 件
```

そのうえで、車両 track（1〜7。track 0 は全編に写る静止物なので除外）が
2 つ以上あるフレーム 1615 枚・ペア 3388 件を分類した:

| 量子化前の差 | 件数 | 割合 | どこで失われたか |
|---|---:|---:|---|
| `== 0` | 90 | **2.7%** | 深度側。**量子化より前**から同値 |
| `0 < 差 < 0.002` | 1221 | **36.0%** | **量子化で消えた**（実在する差が刻み幅より小さい） |
| `>= 0.002` | 2077 | 61.3% | 残る |

**答え: 大半は量子化で失われている。** 深度側の限界は 2.7% しかない。

そちらの集計（`anchor_z` 単調 95%、同値 32%）はこちらでも再現した
（1615 枚で 95% / 32%、`anchor_v` 92%、`bbox_h` 87%、`bbox_w` 76%）。
フレーム数がそちらの 324 と違うのは母集団の取り方の差だと思うが、比率は全部一致している。

**区間別に見ると、症状の「最初の数秒だけ」と正確に対応する:**

| 区間 | 指標 | 完全順序 | 同値あり |
|---|---|---:|---:|
| 0-300（最初の 10 秒） | camZ（現行 0.002） | **5.3%** | **94.7%** |
| 0-300 | camZ（量子化前 float） | 78.3% | 0.0% |
| 300-900 | camZ（現行 0.002） | 55.9% | 44.1% |
| 300-900 | camZ（量子化前 float） | 97.2% | 0.0% |
| 900-1830 | camZ（現行 0.002） | 89.6% | 0.6% |
| 900-1830 | camZ（量子化前 float） | 89.7% | 0.0% |

配布した修正ビルド（0.0001）を同じ形で並べると:

| 区間 | 指標 | 完全順序 | 同値あり | 逆転あり |
|---|---|---:|---:|---:|
| 0-300 | camZ（現行 0.002） | 5.3% | 94.7% | **0.0%** |
| 0-300 | camZ（修正 0.0001） | **68.3%** | **22.7%** | **10.0%** |
| 0-300 | camZ（量子化前 float） | 78.3% | 0.0% | 21.7% |
| 300-900 | camZ（現行 0.002） | 55.9% | 44.1% | 0.0% |
| 300-900 | camZ（修正 0.0001） | 94.2% | 4.4% | 1.4% |
| 900-1830 | camZ（現行 0.002） | 89.6% | 0.6% | 9.8% |
| 900-1830 | camZ（修正 0.0001） | 89.7% | 0.2% | 10.1% |

**「逆転あり」が 0.0% → 10.0% に増えるのは劣化ではない。**
現行は同値が多すぎて逆転が起こる余地すら無かっただけで、
同値が解けた結果、元から間違っていたペアが見えるようになった。
量子化前の float でも 21.7% 逆転しているので、**修正後の 10.0% はむしろ
量子化前より少ない**（刻みが粗いぶん、微小な誤差が同値に吸収されているため）。
中身は 2.7% の「深度側から同値」と同じ系統の誤りで、新しく増えた誤りではない。

**最初の 10 秒は多対象フレームの 94.7% で同値が起きていて、`anchor_z` は前後関係を
まったく運んでいない。** 量子化しなければ 78.3% は正しい。
車両が近づく後半（900-）は現行のままでも劣化しておらず、量子化は効いていない。
「最初の数秒だけ」がそのまま数字に出ている。

#### 3.5. 再現スクリプトの判定基準について（1 点だけ指摘）

`train_depth_order.py` は **「視点からのユークリッド距離」= `sqrt(x²+y²+z²)`** で
近い順を出しているが、**Unity 上の前後関係を決めるのはこれではなく `camZ`**（view 空間 Z）。
両眼視差も深度バッファも透視除算も効くのは `z` だけで、`x` の横ずれは入ってこない。

この差は無視できる大きさではない:

| 区間 | 指標 | 完全順序 | 逆転あり |
|---|---|---:|---:|
| 0-300 | 視点からの距離 | **0.0%** | **100.0%** |
| 0-300 | camZ（量子化前 float） | 78.3% | 21.7% |

遠ざかる列車は横方向の広がり（`|x|` 差 0.04〜0.08）が `camZ` 差（0.001〜0.03）より
桁で大きいので、**ユークリッド距離で見ると `anchor_z` を何に変えても 100% 逆転のまま**になる。
実際、今回の修正ビルドでもユークリッド距離の一致率は 39.4% → 39.4% で動いていない。

frame 160 も `camZ` で見れば `t1=0.8460 < t2=t3=0.8480` で**順序自体は間違っていない**。
実際に壊れているのは `t2` と `t3` が同値になっていること
（ここは 2.7% の「量子化前から同値」に当たるフレームだった）。

**判定は `camZ` の列で行ってほしい。** 同梱した `anchor_z_order_check.py` は
`camZ` / `camZ（量子化前）` / `視点からの距離` の 3 つを並べて出すようにしてある。

**ここが今回いちばん確認したい点なので、先に書いておく。**

frame 160 は `camZ` では元から正しい順序なので、**今回のビルドを入れても
frame 160 の見え方は変わらない。** 効くのは 0-300（最初の 10 秒）で、
そこは同値フレームが 94.7% → 22.7% に落ちる。**試すならこの区間を見てほしい。**

そのうえで、**もし全編を通して何も変わらなかった場合**は、配置が `camZ` ではなく
別の量（ユークリッド距離など）で決まっているということになる。
こちらが見たのはそちらの Python 移植版だけで、`PinholePlacementSpace.cs` の実物は
見ていないので、そうなったら C# 側を見せてほしい。**そのときは D-008 の原因が
量子化ではなく配置式のほうにある**ことになり、切り分けが変わる。

#### 4. 同一フレーム内の相対順序だけでも保証できるか → `quant_pos_scale` を下げるだけで大半は戻る

`quant_pos_scale` は `anchor_z_q` にしか使っていない
（joints は `quant_joint_scale`、`anchor_scale_q` は定数 65535）。
`anchor_z` は 1 を超えないので int16 の余裕は充分ある:

| `quant_pos_scale` | 全体 完全順序 | 全体 ペア一致 | 同値フレーム | 0-300 完全順序 | max `anchor_z_q` |
|---|---:|---:|---:|---:|---:|
| **0.002（現行）** | 63.5% | 71.8% | 31.6% | 5.3% | 472 |
| 0.0005 | 72.2% | 85.4% | 22.3% | 25.7% | 1890 |
| 0.0002 | 84.6% | 91.6% | 9.0% | 57.7% | 4725 |
| **0.0001（採用）** | **87.1%** | **92.8%** | **5.7%** | **68.3%** | **9449** |
| 0.00005 | 88.7% | 93.6% | 2.7% | 73.3% | 18898 |
| 量子化なし（上限） | 89.9% | 94.2% | 0.0% | 78.3% | — |

**train の配布ビルドは 0.0001 にした。** int16 上限 32767 に対して max 9449 で
3.5 倍の余裕がある。0.00005 のほうがわずかに良いが、余裕が 1.7 倍まで減るので見送った。

**ただし builder の既定値は 0.0002 にしてある。刻み幅が 2 つ出てくる理由を書いておく。**

`anchor_z` が 1 を超えないのは**深度サンプリング由来のアンカーだけ**で、
animal の `animal_camera_root` アンカーは AniMer のカメラ空間 root Z を
そのまま書いており、`1 - disp` ではないので**上限が無い**
（実測レンジは `bundle_animal` で 0.268〜0.748）。

| `quant_pos_scale` | `anchor_z_q` が表せる上限 |
|---|---:|
| 0.0001 | 3.28 |
| **0.0002（既定）** | **6.55** |
| 0.0005 | 16.38 |

既定を 0.0002 にしたのは、animal の実測最大 0.748 に対して約 9 倍の余裕を残すため。
**train は全 track が深度サンプリング由来（`anchor_z < 1` が保証される）なので
0.0001 で安全**、という切り分け。

パイプラインから train を作り直すときは
`--bundle-quant-pos-scale 0.0001` を付ければ配布ビルドと同じになる。
付け忘れると 0.0002 になるが、それでも 0.002 よりは大きく改善する
（全体 84.6% / 同値 9.0%、0-300 完全順序 57.7%）。

なお、int16 に収まらない場合に**黙って値をクランプしていた**のを
エラーで落とすように変えた。クランプすると遠方オブジェクトが全部同じ値に潰れ、
D-008 より悪い壊れ方をするため。

- **schema 変更なし。** フィールドの型も並びもそのまま。変わるのは
  `manifest.json` と `meta.bin` ヘッダの `quant_pos_scale` の**値だけ**。
- **前提の確認をお願いしたい**: `quant_pos_scale` を manifest（または meta.bin ヘッダ）から
  読んでいて、`0.002` をコード側に定数で持っていないこと。
  **もし定数で持っていると `anchor_z_q` が 20 倍になるので、
  配置が丸ごと 20 倍奥に飛ぶ。**
  そちらの `train_depth_order.py` は manifest を優先して読む作りなので
  たぶん大丈夫だと思うが、実機で試す前にそこだけ見てほしい。

#### 4.5. これで直らないもの

900-1830 の区間は、量子化前の float で見ても完全順序 89.7% / 逆転 10.1% で、
**量子化を外しても直らない**。これは深度信号そのものの精度の話で、
**D-004 で開いたままの「`anchor_z` と実距離の相関が低い」問題**と同じもの。
今回の修正はここには効かない。今回の対象は 0-300 の 94.7% 同値のほう。

#### 5. Unity 側のタイブレーク（`anchor_v` / `bbox_h`）について → 不要

**新しい補正機構は足さないでほしい、というそちらの希望どおりで問題ない。**
0.0001 にすれば同値フレームは 31.6% → 5.7% になるので、タイブレークが要る場面がほぼ無くなる。

参考までに、この bundle での各指標の実力は測ってある:

| 指標 | 完全順序 | ペア一致 |
|---|---:|---:|
| `anchor_v`（画面上ほど奥） | 91.6% | 96.0% |
| `anchor_z` 0.0001 | 87.1% | 92.8% |
| `bbox_h` | 86.7% | 91.4% |
| `bbox_w` | 76.0% | 84.4% |

`anchor_v` はこのクリップでは `anchor_z` より強いが、**それは列車が地面に沿って
消失点へ向かう構図だから**で、`v` が実質「地平線までの距離」になっているだけ。
飛ぶ・跳ねる対象では成り立たないので、**汎用のタイブレークに使うのは勧めない。**
