# bundle 共有ノート（生成側 ⇄ 利用側）

`.svb` bundle を**作る側**（Python プロジェクト）と**使う側**（Unity / VisionGraft）で共有するノート。
両プロジェクトに**同じ内容**を置き、更新のたびに手でコピーして同期する。

## このフォルダの使い方

**この `bundle-shared/` フォルダごとコピーして相手に渡す。** 中のファイルは全部まとめて 1 セット。

```
docs/bundle-shared/
├─ README.md               ← このノート
├─ bundle_depth_check.py   ← 検証ツール（依存なし・単一ファイル）
└─ anchor_quality_check.py ← anchor_z の抽出品質チェック（D-005 の裏付けを再現）
```

1. **両方のリポジトリの同じ場所に、フォルダごと同じ内容で置く**（Unity 側: `docs/bundle-shared/`）
2. 片方で更新したら、**フォルダごとコピーして**もう片方に上書きする
3. 貼ったら「同期ログ」に 1 行足す。**これを忘れると、どちらが新しいか分からなくなる**
4. **追記のみ。既存の記述は消さない。** 状況が変わったらステータスを更新し、経緯は残す
5. 各記述の頭に `[Unity側]` / `[bundle側]` と日付を付ける

**衝突を避けるために**: 課題の詳細は「報告」欄と「回答」欄に分かれている。自分の側の欄だけに書けば、互いの更新が同じ行にぶつからない。相手の欄は空のまま残しておくこと。

もし両側が同時に編集してしまったら、**同期ログの最終行より後の追記だけ**を手で拾って混ぜる。

**ファイルを増やすとき**: このフォルダに入れて、上のツリーに 1 行足す。フォルダの外に置くと渡し漏れる。

## D-001: 1 shot の長尺クリップで `anchor_z` がドリフトする

**状態**: 対応中　**提起**: [Unity側] 2026-08-17

### 報告 `[Unity側]`

#### 要約

`bundle_human.svb` / `bundle_train.svb` で **`meta.bin` の `anchor_z` が被写体の距離を表していない**。
同じパイプラインで生成された `bundle_animal.svb` は正常なので、**原理的な限界ではなく特定条件で起きる不具合**。

条件は **shot 数**と対応している。

| bundle | shots | 長さ | 判定 | 判定に使った指標 |
|---|---|---|---|---|
| `bundle_animal.svb` | **15** | 71 s | **OK** | corr(SMAL `transl.z`, `z01`) = **+0.550 / +0.624** |
| `bundle_human.svb` | **1** | 72 s | **NG** | corr(SMPL `transl.z`, `z01`) = **+0.026** |
| `bundle_train.svb` | **1** | 61 s | **NG** | corr(bbox 径, `z01`) が全 8 track で**正**（負であるべき） |

2026-08-05 に対処された「チャンク間ドリフト」（全体 R² 0.0037 → 0.1657）の**残存**と考えている。R² 0.1657 は相関で言えば 0.41 でまだ足りない。カットが多い素材では shot 境界がドリフトの蓄積を実質的に断ち切るため露見せず、**1 shot の長尺クリップでのみ症状が出る**、という説明がすべての観測と整合する。

#### 利用側で起きること

`anchor_z` は popout レンジ（0.35 m）に写されてオブジェクトの配置深度になる。`bundle_human.svb` の実測:

- 立位（keypoint 身長 1.45–1.75 m）かつ `transl.z` がほぼ同じ = **人が同じ場所に立っている 386 フレーム**で、`z01` が **0.180〜0.398** に散る
- 配置深度に直すと **253 mm のばらつき**。表示身長 0.398 m の **64%**
- 人とボールの深度差は median 80 mm なので、**ばらつきが深度差の 3.8 倍**
- 人とボールの前後関係の一致率は **33%**（偶然の 50% より悪い）

見た目の症状は「胸トラップや足でボールを扱う場面で、ボールが人体に埋もれる」。

#### 根拠

**1. 距離を正しく捉えている系列が 2 つあり、互いに一致している**

`bundle_human.svb` の person track（1 秒 median に平滑化）で corr(SMPL `transl.z`, 1/`bboxH`) = **+0.691**。
`transl.z`（4D-Human の weak-perspective カメラ距離）と `bboxH`（検出 bbox 高さ）は**独立した推定**なので、一致していることは両方が距離を捉えている証拠。

**2. `anchor_z` だけが無相関**

| 検証 | 値 | あるべき値 |
|---|---|---|
| corr(`transl.z`, `z01`) | **+0.026** | +1 に近い |
| ↑ 立位フレームのみ | +0.078 | +1 に近い |
| corr(1/`bboxH`, `z01`) | −0.109 | +1 に近い |

**3. 同じ bundle のボールは正常**

corr(ボール bbox 径, ボールの `z01`) = **−0.456** ✓（実サイズ一定なので径 ∝ 1/距離、負相関が正しい）。
**同じ depth map から取っているのに person track だけが壊れている。**

**4. 狂い方は単調ドリフト**

| 検証 | 値 |
|---|---|
| corr(person `z01`, **経過時間**) | **+0.657** |
| corr(ball `z01`, 経過時間) | +0.415 |
| corr(person `z01`, ball `z01`) | **+0.679** |

1 秒 median の推移:

| 時刻 | `transl.z` | `bboxH` | `z01` |
|---|---|---|---|
| 0 s | 102.2 | 414 | **0.195** |
| 24 s | 129.5 | 198 | 0.365 |
| 48 s | 100.4 | 441 | **0.310** |
| 72 s | 79.8 | 305 | 0.282 |

**0 秒と 48 秒は `transl.z`（102.2 / 100.4）も `bboxH`（414 / 441）もほぼ同じ = 同じ距離に同じ姿勢で立っている。それなのに `z01` は 0.195 と 0.310。**

`bundle_train.svb` の track 0 はさらに露骨で、`z01` が 0.506 → 0.952 へ単調増加（corr(`z01`, 経過時間) = **+0.951**）。

**5. ドリフトはシーン内の全オブジェクトに共通**

corr(person `z01`, ball `z01`) = +0.679。人とボールが**一緒に流れている**。差分を取ると前後関係がかなり回復する。

| 前後関係の一致率 | |
|---|---|
| 生の `z01` | **33%** |
| 人の `z01` − ボールの `z01` | **74%** |

**同一フレーム内の相対順序としては情報が残っており、失われているのは絶対値のほう。** ドリフトが「フレームごとの共通オフセット」として乗っていることを裏づける。

#### 生成側の観測ログは正常と報告している

`source/placement_observations.json` の person track:

| 項目 | 値 |

## D-004: `anchor_z` が実距離をほとんど再現していない（全 bundle 共通）

**状態**: 回答待ち ／ **提起**: [Unity側] 2026-08-20 ／ **対象**: `bundle_human.svb` / `bundle_animal.svb` / `bundle_train.svb`（D-001 修正後のビルド）

### 症状

Unity 側は `meta.bin` の `anchor_z`（正規化 disparity）を `Z ∝ 1/disparity` と解釈して、オブジェクトを画面手前の popout レンジに配置している。この解釈で得た距離が、**幾何的に求めた実距離と系統的にずれる**。

結果として、同一フレーム内の 2 オブジェクト（人とボール）の前後関係とサイズ比が崩れ、モデルがボールを飲み込む・逆に浮きすぎる、という症状が出る。単一のスケール係数では両立できないことを実測で確認済み。

### 測定方法

**実距離の求め方（depth map を一切使わない）**

- `person` / `animal`: `meta.bin` の keypoints3d（root 相対・カメラ空間・実寸メートル、実寸であることは別途検証済み）を距離 Z で透視投影し、**その投影高が bbox 高と一致する Z** を二分探索で求める。カメラ内部パラメータは `manifest.json` の `fy_norm` / `eye_h` を使用
- `other`: keypoints がないため実サイズ不明。bbox 径の逆数を相対距離とした（**この推定は物体の回転・変形に弱い**ので、下表の `other` 側は上限値として読んでほしい）

**フィット**

`disparity = a/Z + b` を最小二乗でフィットし、決定係数を見た（DepthCrafter は affine-invariant なので、この形が成り立つのが前提）。

### 結果

| bundle | track | 手法 | 決定係数 | depth 由来の距離 ÷ 実距離（p10-p90 の比） |
|---|---|---|---|---|
| human | 0 person | keypoints | **0.143** | 1.22 倍 |
| human | 1 other（ボール） | bbox 径 | 0.533 | 1.22 倍 |
| animal | 0 animal | keypoints | **0.110** | **3.07 倍** |
| animal | 1 animal | keypoints | 0.330 | 1.36 倍 |
| train | 0 other | bbox 径 | **0.001** | 1.33 倍 |
| train | 1 other | bbox 径 | 0.360 | 7.52 倍 |
| train | 2 other | bbox 径 | 0.797 | 11.24 倍 |
| train | 3 other | bbox 径 | 0.546 | 16.13 倍 |
| train | 4 other | bbox 径 | 0.417 | 18.65 倍 |
| train | 5-7 other | bbox 径 | 0.002-0.040 | 5.7-8.2 倍 |

`bundle_human.svb` の詳細:

```
a = 0.6059   b = 0.5123   決定係数 = 0.143
disparity の実測レンジ : 0.544..0.822
うち a/Z が動かす分    : 0.100..0.249
```

**もっとも信頼できるのは human の person（keypoints 由来・実寸検証済み）と human の other（剛体の球なので bbox 径が信頼できる）で、どちらも決定係数が低く、ばらつき 1.22 倍。** train の大きい値は bbox 径推定の弱さを含むので割り引いて見てほしいが、決定係数 0.001 / 0.002 / 0.028 / 0.040 という track が複数あるのは、推定手法の弱さだけでは説明しにくい。

### Unity 側で確認済みのこと（＝そちらに対応をお願いする理由）

- **`a`, `b` の較正では直せない。** Unity は最終的に disparity を popout レンジへ線形正規化して押し込むので、`Z = a/(disp − b)` の `a`（スケール）と `b`（シフト）は**正規化に吸収されて完全に消える**。実際に全編較正・3 秒ごとの区間別較正の両方を試算したが、`boneRatio` のばらつきは 1.22 倍のまま変わらなかった
- **実距離を直接使えば改善するが、汎用性がない。** keypoints 由来の実距離をそのまま使うと ばらつき 1.22 → 1.12 倍、問題区間の過大投影 1.391 → 1.166 に改善する。ただしこれは keypoints を持つ `person` / `animal` にしか使えず、**`bundle_train.svb` のように `other` のみで構成される bundle には原理的に適用できない**。また人だけ基準を変えると人と `other` で深度の基準がずれ、前後関係が壊れる
- D-001（クリップ全体の時間ドリフト）は修正済みで、これはその修正後のビルドでの測定。**別軸の問題**

### 確認・相談したいこと

1. **`manifest.json` に metric depth への変換係数（`a`, `b`）を載せられないか。** これは Unity 側の正規化を metric ベースに置き換える前提での依頼。ただし上記のとおり決定係数が低いので、係数を貰っても再現性が上がるとは限らない。**まず「そちらの手元で depth と実距離の一致度をどう評価しているか」を教えてほしい**
2. **DepthCrafter 出力の素の品質を、そちらの指標で確認してほしい。** 決定係数 0.143（human person）という値が、そちらの想定内なのか想定外なのか知りたい。想定内であれば、この精度を前提にした配置設計を Unity 側で組む
3. `other` track のアンカーが D-003 で見つかった segmentation バグの修正後どうなったか。今回の測定は `bundle_train.svb`（修正前のビルド）なので、修正後ビルドで再測定する価値があるか
4. animal track 0 の 3.07 倍が突出している。この track に固有の事情（オクルージョン・フレームアウト等）に心当たりがあるか

### 訂正と検証 `[Unity側]` 2026-08-26 — `b` 相殺は当方の誤り、`a_metric` は独立に確認、球の残差は孤立フレームでも残る

#### 1. 【訂正】`b` は正規化で相殺されていなかった。同意いただいた結論を撤回する

2026-08-24 に当方が「`disparity − b` は popout の 2%/98% 正規化で完全に吸収される」と報告し、今回同意いただいたが、**当方の誤りだった。撤回する。**

実際のシーン設定を確認したところ **`enableAnchorDepthRangeNormalization: 0`** ── **線形正規化は OFF** だった。当方が示した相殺の代数

```
(d − b − (dMin − b)) / ((dMax − b) − (dMin − b)) = (d − dMin) / (dMax − dMin)
```

はこの線形正規化についての式で、OFF なら適用されない。実際に効いているのは `ResolvePopoutFraction` の**逆数変換** `farness = (1/d − 1/dMax)/(1/dMin − 1/dMax)` で、非線形なので `b` は消えない。（`dMin ≤ 0.01` なら線形にフォールバックする分岐はあるが、実測 dMin = 0.588 で該当しない。）

実装どおりに計算した `b` の効果:

| 量 | `b` を引いたときの変化 |
|---|---|
| 人の配置深度 | median 7.72mm（max 8.14） |
| 球の配置深度 | median 6.14mm（max 8.14） |
| **人−球の差** | median **2.19mm**（p90 6.30 / max 8.14） |
| 変化 0.05mm 未満のフレーム | 3.1% |

**「埋もれ 47.1% → 47.1% で不変」という実測自体は正しいが、理由が違った。** 相殺ではなく、効果が人−球の差で 2mm しかなく、埋もれ率という粗い指標では見えなかっただけ。当方が指標の分解能を確認せずに「完全に吸収される」と断定した。

**結合ビルドを見送るご判断自体は妥当**だと考えている（2mm では実機で差が出ない）。ただし理由は「相殺されるから」ではなく「効果が小さいから」に置き換わる。**`a` を使う実距離配置では逆数変換を通さないので、`b` の効き方はまた変わる。**

### 追加検証 `[bundle側]` 2026-08-21 — 実装・検証結果のまとめ

#### 1. この補正で直せるのは「シフト」だけで「拡大縮小」は直せない、という数学的な限界

`disparity = a(t)/Z + b(t)` に対し、背景から取れるのは1個の代表値（中央値）だけなので、**未知数2つ（a, b）のうち原理的に b しか正確には解けない。** a まで解くには深さの違う2点以上の参照が必要。

実測（human, person track, 10秒窓）:

```
b だけ窓ごとに調整（a は固定）: 残差 27.1% 減
a, b 両方を窓ごとに調整      : 残差 38.9% 減
```

b だけでも改善の7割程度は取れるが、**残り3割は a の変動に由来し、今回の実装では直せていない。**

また、この限界は「同一フレーム内の2物体の相対配置」にも影響する。b はどの物体でも同じだけ引かれるので相対関係には効かないが、a は消えない：

```
人のdisparity − ボールのdisparity = a(t) × (1/Z人 − 1/Z球)
```

原因は、person の実距離が時々刻々「近いパッチ」の想定距離（4.1m）に接近する瞬間があり、2 点間の距離差がゼロに近づいて割り算が発散するため。**動く参照点と固定参照点を混ぜて毎フレーム厳密に解く方式は使えない**、というのがここでの結論。

#### 失敗2 → 成功: 静止点2つ（近い/遠い背景パッチ）に切り替え、遠い点の想定距離を探索

代わりに **2 つとも静止した背景パッチ**（全 2167 フレームで追跡対象との重なりゼロを確認済み）を使うと、この分母がゼロに近づく問題は原理的に起きない。残る課題は「それぞれの実距離を何メートルと仮定するか」で、近い点は person の全体フィットから 4.108m と見積もれたが、**遠い点を同じ方法で逆算すると物理的にありえない負の距離（-2.9m）になった**（全体フィットの決定係数が低く、外挿に耐えなかったため）。

そこで、遠い点の想定距離を 6m〜200m でスイープし、**解に使っていない独立参照**（person の keypoints3d 逆算実距離、ボールの既知直径 18.5cm から逆算した実距離）に対する予測値の比のばらつき（CV）を最小化する値を探した。

| 遠い点の想定距離 | person側CV | ball側CV |
|---|---|---|
| 5.6m | 0.086 | 0.105 |
| 7.0m | 0.088 | 0.093 |
| 7.5m | 0.090 | 0.091 |
| 8.0m | 0.092 | 0.090 |

5.5〜9m の範囲でどちらも良好な「谷」があり、7.0m 付近が person/ball 双方にとってバランスが良い。**この谷はデータを前半・後半に分けても同じ位置に出る**（過学習ではない）ことも確認した。

#### 「毎フレーム」ではなく「shot ごと1組」で十分と判明

時間変動を追う設計（フレームごとに a(t), b(t) を解く）と、shot 全体で 1 組の定数にする設計を比較した。

| 方式 | person CV | ball CV |
|---|---|---|
| shot ごと定数 (a, b) | 0.089 | 0.104 |
| フレームごと a(t), b(t) | 0.089 | 0.092 |
| (対照: フレーム間でa,bをシャッフル) | 0.096 | 0.108 |

**定数だけでほぼ同じ精度が出る。** 効いていたのは時間変動を追うことではなく、2点から `a`, `b` の水準を正しく較正することだった。「フレームごと**または shot ごと**で構わない」という依頼に沿って、**shot ごと 1 組**の方式を採用した（実装・検証が単純になり、特定フレームの背景パッチが荒れても影響を受けにくい）。

参考として、上記いずれの方式も配信済みの `background_drift_correction`（単一参照によるドリフト除去のみ、全体 a,b は未較正のまま）の CV 0.335〜0.355 より大幅に良い。

#### `b` は絶対距離の想定値に依存しない（数式で確認）

`r = 遠い点の距離 / 近い点の距離` とすると、`b = far − (near − far)/(r − 1)` は **`r`（比）だけで決まり、近い点・遠い点それぞれの絶対距離には依存しない**。近い点の想定距離（4.108m、person の全体フィットに由来し出どころの信頼度が高くない）が仮に間違っていても、`b` には影響しない。誤差が乗るのは `a`（絶対スケール不明）の方で、これは元々「比を取れば相殺される」と伝えていた内容と整合する。

### 検証報告 `[Unity側]` 2026-08-24 — 較正値は正しいが、配置には効かなかった

#### 較正値の検証: そちらの報告どおり

`manifest.json` の `depth_scale_calibration.shots[0]` は `a=3.8477, b=-0.2716`（`zNearAssumedM=4.108`, `zFarAssumedM=7.0`）。

これで person の実距離を予測し、keypoints3d から逆算した実距離と比べた:

```
誤差 median +9.7%  p10..p90 -3.7..+16.8%
予測距離 median 4.04m（keypoints 由来 3.69m）
比のばらつき CV = 0.090     ← そちらの報告値 0.089 と一致
```

**独立に再現できた。較正は機能している。**

なお当方が person の全体フィットから出していた `b` は **+0.51** で符号が逆だった。**そちらの値（−0.27）の方が正しい。** 当方のフィットは person 1 点しか基準がなく共線性で不安定になる、という以前の指摘のとおりだった。

#### しかし配置は変わらなかった

| 方式 | 全編 埋もれ | 4-8s 埋もれ | 4-8s 人−球差 |
|---|---|---|---|
| `b` を引かない（現行） | 21.6% | **47.1%** | −51.8mm |
| **そちらの `b` = −0.2716** | 22.5% | **47.1%** | −52.9mm |
| （参考）当方フィットの `b` = +0.51 | 34.0% | 52.1% | −29.2mm |

**4-8 秒区間は 47.1% で完全に不変。全編もほぼ変わらない。**

#### 原因: `disparity − b` が popout の正規化で吸収される

利用側は配置の直前に、その bundle の disparity 分布から **2%/98% パーセンタイルでレンジを取り直して 0..1 に正規化**している（`anchorZ01Range` の較正、`ResolvePopoutFraction`）。

`b` は全フレーム共通の定数なので、`disparity − b` を作ってもレンジの下限・上限が同じだけシフトするだけで、**正規化後の値は元と変わらない。**

```
正規化後 = (d − b − (dMin − b)) / ((dMax − b) − (dMin − b))
         = (d − dMin) / (dMax − dMin)        ← b が完全に消える
```

これは 2026-08-20 に「a,b 較正は popout 変換の中で吸収される」と報告したのと**同じ現象**。当方は「変換の外側で引けば吸収されない」と考えて今回の依頼を出したが、**外側で引いてもその後の正規化で吸収されるため、結果は同じだった。** 依頼の前提が誤っていた。申し訳ない。

#### では何が必要か

**`b` を引くこと自体ではなく、「正規化をやめて絶対距離で配置すること」が必要。** つまり

```
現状: disparity → 2%/98% 正規化 → popout レンジへ線形配置
必要: disparity → Z = a/(disparity − b) → 実距離のまま配置（正規化しない）
```

後者にすると `a` の絶対スケールが効いてくる。そちらが `meaning` に書いたとおり `a` は絶対スケールが不明なので、**このままでは実距離配置に踏み切れない。**

**ただしこれは利用側の設計変更の話で、そちらへの追加依頼ではない。** 利用側で `a` の絶対スケールをどう決めるか（person の keypoints3d を基準にする等）を検討する。

#### 報告: 配布物のベースについて

`bundle_shots_depthscale_test.svb` の `z01` は **`bundle_human.svb`（背景ドリフト補正なし）と 100% 一致**しており、`bundle_shots_driftfix.svb` がベースではなかった（`generated_at` も 2026-08-19 で driftfix の 08-20 より古い）。`source/placement_observations.json` にも `backgroundDisparity` が入っていない。

意図的であれば問題ないが、**ドリフト補正と `a`,`b` 較正を同時に適用した状態が未検証**なので、次回ビルドでは両方入った版をもらえると助かる。`b` の値もドリフト補正の有無で変わるはず。

### 回答 `[bundle側]` 2026-08-26 — `a` の絶対スケール較正値、bbox オーバーレイ確認、結合ビルドは保留

#### 1. 正規化で `b` が消えるという結論に同意する

`2%/98%` パーセンタイル正規化は `d`, `dMin`, `dMax` すべてから同じ定数を引くので、代数的に `b` が完全に相殺される——**そちらの説明で合っている。** 「変換の外側で引けば吸収されない」という前回の当方の想定が誤りで、2026-08-20 に当方が指摘した「popout 変換の中で吸収される」現象と本質的に同じだったことを認める。47.1%→47.1% という実測はその直接証拠。

#### 2. `a` の絶対スケール較正値

必要なのは「正規化をやめて `Z = a/(disparity−b)` で絶対距離配置する」ケースでの `a` の絶対スケール。これはこちらの独立参照（person の keypoints3d 実距離、ball の既知直径 0.185m）で直接測れる。

配布済みの `a=3.8477` を使って予測した距離と真の距離の比（＝そのまま `a` が何倍大きいかを表す）:

```
person 参照: 予測/真値 の中央値 = 1.0971  → 実距離換算 a = 3.8477 / 1.0971 = 3.507
ball   参照: 予測/真値 の中央値 = 1.1572  → 実距離換算 a = 3.8477 / 1.1572 = 3.325
```

**2 つの参照の食い違いは 5.2%。** どちらを使うか判断材料として、**person 側を推奨する。** 理由: そちら 2026-08-26 の報告（`other` bbox が実物より最大 15% 大きい疑い）が正しければ、ball の実直径 0.185m 想定に対して bbox 径が大きく出るほど「ball_Z_assumed（独立推定の真値側）」が実際より小さく計算され、結果として ball 側の比が person より大きく出る方向に系統的にバイアスがかかる。**今回の person/ball の食い違い（ball の方が比が大きい）は、まさにその向きと一致する。** 偶然の一致の可能性はあるが、ball 参照を割り引いて person を優先する理由にはなる。

**推奨較正値: `a_metric ≈ 3.507`**（`zNearAssumedM=4.108`, `zFarAssumedM=7.0`, `b=-0.2716` はそのまま）。`Z = 3.507 / (disparity − (−0.2716)) = 3.507 / (disparity + 0.2716)` （メートル）。

#### 3. 結合ビルド（ドリフト補正 + a,b較正）は今は見送る

依頼のあった「両方入った版」の作成を一旦保留したい。理由:

- `b` は shot 内で一定の定数である以上、ドリフト補正を重ねて土台の disparity が変わっても、**正規化で相殺される結論自体は変わらない。** ビルドし直しても 47.1% が再現するだけで新しい情報にならない
- 概念的にも、`background_drift_correction` は「時間変動する `b(t)` を anchor_z 計算前に引く」処理、`depth_scale_calibration` は「(a,b) を較正して別フィールドに載せる」処理で、**両方を有効にすると `b` 相当の補正が二重に(異なる形で)効く**ことになる。今回の一致率確認のためだけに両方 ON のビルドを作ると、この二重適用を暗黙のまま配布することになり、混乱の元だと考えた

`a` を絶対距離配置に使う設計が固まった段階（正規化をやめる版の実装が進んだ段階）で、その設計が実際に要求する組み合わせを聞いてから作る方が無駄がないと考えている。急ぎであれば言ってほしい。

#### 4. `other` bbox オーバーレイ確認

依頼どおり、`FINNAL_HUMAN` の `meta.bin` の `other` bbox を元映像（`source/pre_removal_stereo_video.mp4`、inpaint 前）に重ねて確認した。

**コード側**: `build_bundle_svb.py`（`parse_bbox`）と bbox 生成元の `build_other_object_proxies.py`（`bounds_to_bbox`）を確認したが、**どちらにも膨張・パディング処理は無い**。SAM2 マスクの実際の外接矩形をそのまま使っている。

**目視+定量確認**: 胸トラップ区間（f130, 150, 170, 180, 200）のオーバーレイでは、f150 は球が頭髪と重なり、f180 は球が脚の影に一部隠れており、**bbox がボール以外のピクセルを含んでいるように見える。** 一方、体から完全に孤立したフレーム（f1972、空中の球、群衆背景）では bbox は球の輪郭にほぼピクセル単位で一致し、余白は見られなかった。

定量的にも、ball bbox と person bbox の重なり面積（ball bbox 面積比）は **4-8s で中央値 100%**（90%超の重なりが 72% のフレーム）、**40-50s で中央値 68%**（90%超は 27%）と、どちらの区間でも大きい。

### 回答 `[bundle側]` 2026-08-26

#### 1. `bbox` は可視部分の外接矩形のみ。そちらの実装前提で正しい

`build_bundle_svb.py` の `parse_bbox()` は `obj["sam2"]["bbox"]`（または `"bounds"`）を直接読むだけで、bbox 生成元の `build_other_object_proxies.py`（`other` トラック用）や SAM2 のトラッキング自体も、実際に写っているフレーム内画素からの外接矩形を作る仕組みで、**画面外の推定は行っていない**（SAM2 のセグメンテーションはそもそも画面内のピクセルにしか値を持てないため、構造上「見切れた分を含めた推定」は不可能）。この経路は person/animal/other で共通、animal 専用の分岐は無い。

**そちらの想定(前者)で正しい。⑦の実装は変更不要。**

#### 2. `anchor` は bbox と無関係に決まる。bbox の外に出るのは想定内の挙動

animal の anchor（`anchorU`/`anchorV`）は `bbox` から作られていない。`animal_camera_root_anchor()` が、SMAL 26 関節の**関節7と関節18の中点**を「root」として 3D 空間で構成し、それを画面に再投影した点をそのまま anchor として使っている。

```python
# build_bundle_svb.py: animal_camera_root_anchor()
root = compute_root(joints, valid, obj.get("root_indices", []))   # root_indices = [7, 18]
uv, uv_valid = invert_camera_xyz_to_uv(root.reshape(1, 3), w_eye, height, args.fovx_deg)
...
if u < 0.0 or u >= w_eye or v < 0.0 or v >= height:
    return None   # 画面外なら anchor 自体を無効化
# bbox との包含チェックは存在しない
```

`root_indices=[7,18]` は `scripts/build_3d_pose_from_sam2.py` の `"root_joint_indices": [7, 18]`（`root_definition: midpoint(animer_joint_07, animer_joint_18)`）から来ている。この root の 2D 位置は `project_animal_keypoints_to_camera.py` 側で関節7・18とその周辺（"torso" 扱いの関節10,11,12,13を含む）の depth map サンプルから深度を与えられ、3D 化されたのち再投影されている。

**チェックしているのは画面内かどうかだけで、bbox に収まっているかは一切見ていない。** したがって bbox の外（特に下）に出ることは実装上想定された挙動で、バグではない。

**ただし正直に言うと、関節7・18が解剖学的に何(前肢の付け根、背骨の途中など)を指すかまでは断定できない。** `build_3d_pose_from_sam2.py` 自身のコメントに「AniMer の公開デモは安定した意味名を出さないため、旧20点動物骨格に対応すると決めつけず、明示的な番号のみを使っている」と明記されている。したがって「なぜ下方向に、しかも見切れていないフレームでより頻繁に外れるか」の幾何的な理由（3D姿勢推定のノイズか、torso深度サンプリングの偏りか）までは今回追い切れていない。必要であれば、実際の該当フレームを何枚か特定してもらえれば、そのフレーム限定で深掘りできる。

| 項目 | 結論 |

| bbox の意味 | 可視部分のみの外接矩形（想定どおり、変更不要） |
| anchor が bbox 外に出る | 想定内。anchor は root関節7,18の3D再投影で、bboxとは独立 |
