# Permanent frame-out: indefinite linear walk until off-screen, then hide

When the system frame-out trigger fires and `TryPrepareFrameInTarget` finds no reappearance frame in the remaining metadata, the previous implementation walked the model to a fixed `control` point (2 seconds × walk speed × 1.5 multiplier from the last visible position) and left it frozen there indefinitely in `Owned` stage. The model stayed visible at an arbitrary world position, no random events could fire, and the `Owned` stage never resolved — a state the system had no defined exit from.

The new behavior for permanent frame-outs (`hasFrameInPosition == false`) is to walk the model linearly and indefinitely in `frameOutDirection` at constant speed (`walkSpeed × SystemTriggerSpeedMultiplier`) until either (a) `Renderer.isVisible` becomes false for all renderers on the instance, or (b) a safety timeout of `vp.length × 0.5` seconds elapses from the frame-out moment. At that point the instance is deactivated (`SetActive(false)`), the state resets to `Inactive`, and `hasLiveSample` is cleared so the system trigger does not immediately restart on the next frame. When the video loops and the track reappears in the metadata, `ObserveInteractiveMotionLiveTrackedSample` sets `hasLiveSample` again and normal tracking resumes as expected.

Constant speed was chosen over the existing `ResolveLoopPose` smoothstep easing because the smoothstep curve is anchored to a finite segment (start → control): extending it by moving `control` far away would put the model in the slow "ease-in" phase for the entire visible portion of the walk, visibly out of sync with the constant-pace walk animation clip. A simple linear extrapolation keeps root movement speed consistent with the animation.

`Renderer.isVisible` was chosen over an explicit frustum/viewport check because Unity evaluates it against all enabled cameras automatically, covering both VR eyes without any camera reference wiring. The 1-frame culling lag is acceptable. The half-video-length timeout is a backstop for degenerate cases (frame-out direction pointing toward the viewer, very slow walk speed) where the model might never leave the camera frustum.

Temporary frame-outs (`hasFrameInPosition == true`) are unaffected — they continue to use `ResolveLoopPose` for the timed out-and-back arc toward the predicted reappearance position.
