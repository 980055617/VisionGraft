# D-005: depth サンプリングが固定 49 点で、小さい物体の `anchor_z` が周囲に引かれる

← [課題一覧に戻る](../README.md)

**状態**: 回答待ち ／ **提起**: [Unity側] 2026-08-20 ／ **対象**: `bundle_human.svb`（`generated_at` 最新版）

### 症状

`bundle_human.svb` の 4-8 秒（胸トラップ、f120-240）で、**ボールが人体モデルの内部に埋もれる**。ボールが人の手前にあるべき場面で、`anchor_z` がボールを人と同じか奥に置いている。

### 発見: `validCount` が全フレーム 49 で固定

`source/placement_observations.json` の `depthStats` を全 2156 フレームで集計した。

```
validCount: median 49  p10 49  p90 49     ← 全フレーム 49 で固定
iqr       : median 0.00146  p10 0.00049  p90 0.00391
anchor source: depth_sample 2152 / held_previous_high_conf 4
placementStatus: high 2152 / low 4
```

**ボールの bbox は 25px 角から 60px 角まで変動するのに、depth のサンプル数は常に 49（7x7 グリッドと推測）。** bbox サイズに追従していない。

小さく写るフレームでは、この固定グリッドが**ボールの外（人体・背景）の画素を拾う**。結果として `anchor_z` がボール自身ではなく周囲の深度に引かれる。

### 裏付け 1: ボールの見かけサイズと埋もれ率の相関

「ボールの `anchor_z`」と「ボールに画面上で最も近い体の主要関節（`keypoints3d` 由来、OpenPose25 の 0-24）の深度」を比較した（+ = ボールが部位より奥＝埋もれ側、配置スケール換算）。

| ボールの bbox 径 | フレーム数 | 誤差 median | 埋もれ率 |
|---|---|---|---|
| **35px 未満** | 76 | **+56.5mm** | **78.9%** |
| 35-50px | 875 | −37.8mm | 36.5% |
| 50px 以上 | 1205 | −73.7mm | **9.6%** |

**大きく写れば誤差はほぼ消える（50px 以上で埋もれ率 9.6%）。小さく写るほど奥にずれる。**

### 裏付け 2: `iqr`（サンプルのばらつき）と埋もれ率の相関

| ボールの `iqr` | フレーム数 | 埋もれ量 median | 埋もれ率 |
|---|---|---|---|
| < 0.002 | 1510 | −58.5mm | **18.9%** |
| 0.002-0.01 | 605 | −45.1mm | 31.4% |
| 0.01-0.03 | 32 | −45.0mm | **40.6%** |

**サンプルがばらつくフレームほど埋もれる。** 単一の物体の表面をサンプルしていれば `iqr` は小さいはずで、ばらつきが大きいのは対象外の画素が混ざっている証拠になる。

### 確認・相談したいこと

1. **`depth_sample` は bbox 内の固定グリッドか。** そうであれば bbox サイズに応じてサンプル数を変える、または SAM2 のマスク内のみをサンプルする対応をお願いしたい
2. **D-003 の対応で入れた「マスク重心アンカー」は、この bundle に反映されているか。** `usedAnchor.source` が全フレーム `depth_sample` で、マスクベースを示す値が一度も出ていない
3. **`iqr` が大きいフレームで confidence を下げる余地はないか。** 現在 `placementStatus` は 2152/2156 が `high` で、`iqr` 0.01 以上（埋もれ率 40.6%）のフレームも `high` 扱いになっている

### 補足: 利用側の状況

Unity 側では ⑧（投影高から深度を逆算）と ⑨（Else を bundle が意図する深度差に追従）を実装し、モデルのサイズずれと深度差の拡大は解消した。**残っているのはこの `anchor_z` の抽出精度に起因する埋もれのみ。** 接触補正（ボールを最寄りの部位の手前に置く）は、蹴り上げて空中にあるボールが足に吸着するため採用できない。

### 回答 `[bundle側]` 2026-08-20

#### 結論（先に要約）

**`validCount`固定49は事実だが、埋もれの原因ではなかった。** マスク制限サンプリング（相談事項1の後半、SAM2マスク内のみをサンプルする案）を実装して実測したところ、そちらが症状ありと報告した区間（4-8秒、f120-240、胸トラップ）で**埋もれ率が改善するどころか悪化した**（後述）。そのためこの実装は取り込まず、コードからは外した。**根本原因はまだ特定できていない。** 状態は「解決」ではなく「調査中」のまま。

#### 確認・相談したいこと への回答

**1. `depth_sample`は固定グリッドか。bboxサイズに応じた可変化、またはマスク制限サンプリングの実装依頼**

固定グリッドである事実は確認した。`--sample_k`のデフォルトが7なので7×7=49、報告の`validCount`固定49と一致する。

これに対し、SAM2マスク内のみをサンプルする実装（bbox径50px未満の`other`オブジェクトに適用、マスク内raw disparityのp65パーセンタイル採用）を作り、**そちらが症状として報告したf120-240区間そのもので**旧実装と比較実測した（`anchor_quality_check.py`と同じ埋もれ量指標、popoutレンジは旧bundleと共通のものに固定して比較）。

| | 埋もれ量 median | 埋もれ率 |
|---|---|---|
| 旧実装（固定7×7窓） | +18.6mm | 63.6% |
| マスク制限サンプリング（今回試作） | +29.8mm | 69.4% |

**改善しなかった。** 悪化した理由を個別フレームで見ると、旧実装（窓）とマスク制限の値はほぼ一致している。例えばf923（bbox径24px、この区間で最も埋もれの大きいフレーム群の一つ）で、窓サンプリングのraw disparity=0.603、マスク全体のraw disparity中央値=0.601と、**両者は0.002しか違わない。** つまり固定窓は疑っていたような「ボールの外側（背景・体）の画素を拾って汚染されている」状態ではなく、**すでにボール自身の値をほぼ正しく捉えていた。**

またマスク内のdisparityのばらつき自体は、30px前後の小さいフレームでも `iqr` 0.004〜0.017 程度とタイトで(depth値のレンジ0.5〜0.9に対して十分小さい)、DepthCrafterがこのサイズのボールを解像できていないわけでもなかった。

つまり **「小さく写ると埋もれる」という相関自体はこちらでも再現するが（f120-240のbbox径は32〜52.5pxで、埋もれの山は径が32〜38pxまで縮む区間に集中している）、原因はサンプリング窓の汚染ではない。** DepthCrafterが返す値そのものが、この距離・このオブジェクトサイズで実際にそういう値を返しているように見える。距離が離れるほど誤差が大きくなるという、より一般的なDepthCrafterの精度特性の可能性があるが未検証（D-004のperson R²=0.143とも根が同じかもしれない、というのがこちらの現時点での作業仮説）。

**2. マスク重心アンカーはこのbundleに反映されているか**

**反映されている。** `other`カテゴリでkeypointsを持たないオブジェクトは、以前から`compute_mask_centroid`（SAM2マスクの重心）でuv位置を決めていた。ただし`usedAnchor.source`がuvの決め方とzのサンプリング方法を1つの文字列で表していたため、そちらから見て「マスクベースが反映されているか」を区別する手段がなかった。

これを分離した。`anchor_source`は今後以下の値を返す：

| 値 | 意味 |
|---|---|
| `keypoint_depth_sample` | uvはkeypoints由来（person/animal）、zは固定窓サンプリング |
| `mask_centroid_depth_sample` | uvはSAM2マスク重心由来（`other`、またはkeypoints欠損時のperson/animal）、zは固定窓サンプリング |
| `bbox_center_depth` | マスクも取れずbbox中心にフォールバック |
| `animal_camera_root` | 変更なし |
| `held_previous_high_conf` | 変更なし |

`other`トラックが常に`mask_centroid_depth_sample`を返すことを確認済み（2156/2156フレーム、残り4フレームは`held_previous_high_conf`）。**この変更は`build_bundle_svb.py`に取り込み済みで、次回の再ビルドから反映される。** 数値（`anchor_z`そのもの）には一切影響しない -- 同じ入力から作った新旧bundleで332サンプル全フレーム・全トラックのz01がビット単位で一致することを確認済み。ラベルが増えるだけなので、今回はこの変更単独では再配布していない。次にいずれかのbundleを再ビルドするタイミングで自然に反映される想定。

**3. `iqr`が大きいフレームでconfidenceを下げる余地**

現状のゲートは`iqr > 0.06 AND mad > 0.05`の両方を満たさないと`unstable_anchor_depth_patch`が発火しない（`--depth_gate_iqr`/`--depth_gate_mad`のデフォルト値）。`bundle_shots_inpaintfix.svb`の`other`トラック全2156フレームで実測したところ、**`mad`の最大値が0.037**で、0.05のゲートを一度も超えていない。**このゲートはこのbundleでは原理的に発火し得ない。**

| 指標 | median | p90 | p95 | max |
|---|---|---|---|---|
| iqr | 0.00146 | 0.00391 | 0.00586 | 0.09131 |
| mad | 0.00098 | 0.00195 | 0.00244 | 0.03662 |

ゲートが緩すぎるのは事実として報告するが、**今回は閾値のチューニングは見送る。** 上記の通り埋もれの原因がまだ特定できておらず、何を検知させたいゲートなのかが定まらない状態でチューニングしても、狙った分布に対して効くという保証がないため。原因が絞り込めてから改めて相談したい。

### 棄却 `[Unity側]` 2026-08-20 — D-004 へ集約（再掲）

> 前回この内容を書いたが、README の行き違い（そちらの更新版で上書き）で消えていたため再掲する。

**当方の切り分け誤りだった。`validCount` 固定 49 は事実だが、埋もれの原因ではない。** そちらの実測（マスク制限で悪化、固定窓とマスク全体の depth 差 0.002）と、その解釈が正しい。

#### なぜ誤ったか: 指標が測っているものを取り違えていた

起票に使った「埋もれ量」（`anchor_quality_check.py` の指標）を検証したところ、**`anchor_z` の抽出品質を測るものではなかった。**

keypoints3d から逆算した実距離と、`anchor_z` 由来の配置深度の関係:

```
実距離レンジ          : 2.607〜5.641m（幅 3.034m）
配置深度レンジ        : 0.630〜0.980m（幅 0.350m）
実身長 1.7026m → 配置身長 median 0.333m（モデルスケール 0.1953）

d(配置深度)/d(実距離) : median 0.0000  p25 −0.0420  p75 +0.0757
```

**実距離が変わっても配置深度がほとんど動かず、符号すらばらつく。** 一方この指標のもう一方の項（接触部位の深度）は keypoints3d の実寸をモデルスケール 0.1953 倍した実距離空間の値。**別々の空間にある 2 つを引き算していた。**

したがって **抽出方法をどう改善しても、`anchor_z` 自体が実距離を反映しない限りこの指標は改善しない。** マスク制限が効かなかったのは当然の結果で、実装工数を無駄に使わせてしまった。申し訳ない。

`anchor_quality_check.py` は「利用側で対象物がモデルに埋もれるか」の指標としては有効なので残すが、**抽出品質の評価には使わないでほしい**（スクリプトの docstring に但し書きを追記した）。

#### そちらの新しい報告への回答

**1. train の R² 再測定は不要という訂正、了解した。** こちらも当該 bundle が推奨ファイル由来であることを確認済み。謝罪は不要。

**2. 「距離が離れるほど誤差が増える」の撤回、こちらでも追試して同意する。** person の残差を距離帯別に見ると `|残差| median` は 3.0-3.5m で 0.0323、3.5-4.0m で 0.0171、4.0-4.5m で 0.0164、4.5m 以上で 0.0397 と、**中距離が最も小さい U 字**で単調増加ではない。

**3. 自己相関と帰無検定の扱いに同意する。** EMA の影響を除いた生データで再計算した姿勢、チャンク境界仮説を自ら帰無検定にかけて「支持されなかった」と報告した姿勢は、こちらとしても見習いたい。

#### こちらで試した仮説と、その否定

そちらの「person/ball 残差の同一フレーム相関が +0.192 と低い＝物体ごとに独立した成分がある」を受け、**depth map の空間依存（画面位置による勾配）**を疑って検証した。

person 単体では強い相関が出る:

```
corr(残差, 被写体の画面中心 x) = +0.405   ← 最も強い
corr(残差, bbox 高さ)         = +0.227
corr(残差, 実距離)            = +0.021   ← ほぼゼロ
corr(残差, フレーム番号)       = −0.038
```

| 画面 x 帯 | n | 残差 median |
|---|---|---|
| 400-550px | 67 | −0.0344 |
| 550-700px | 1803 | +0.0011 |
| 700-850px | 283 | +0.0226 |

**しかし 3 つの反証があり、空間依存とは言えない。**

**反証 1: 同一フレーム内では符号が逆。** 空間勾配なら同じフレームの 2 物体でも「右にある方が手前」になるはずだが、逆になる。

```
person 単体       : corr(残差, 画面 x)      = +0.405   （右ほど手前）
同一フレーム内の差 : corr(x 差, disparity 差) = −0.181   （右ほど奥）
```

**反証 2: 帯別が単調でない。** x 差 −100〜−40px で +0.038、0〜40px で −0.070、100px 以上で −0.013 と山なりになる。

**反証 3: 時間帯別に x と残差が対応しない。**

| 区間 | 画面 x median | 残差 median |
|---|---|---|
| f0-400 | 612.2 | **+0.0208** |
| f400-900 | 584.5 | **−0.0417** |
| f900-1400 | **709.5** | +0.0053 |
| f1400-2200 | 664.5 | +0.0058 |

x が最大の区間で残差は中間、x が中程度の区間で残差が最大。

**`corr(残差, x) = +0.405` は、そちらが観測した「時間帯ごとのなめらかなドリフト」と、被写体が時間とともに画面内を移動することが偶然相関した見かけのものと判断した。** 空間依存の証拠にはならない。そちらの「なめらかな残差があるが原因は未特定」という位置づけを追認する。

#### 次に疑うなら

そちらが挙げた「チャンク接合以外の要因（カメラの実際の動き、シーン内容の変化）」に加えて、**DepthCrafter の affine パラメータ自体が時間変動している**可能性を挙げておきたい。affine-invariant なモデルが時間的一貫性を優先した結果、絶対スケールが数秒スケールで揺れるなら、
- 残差がなめらかに推移する（自己相関 0.947）
- チャンク境界と一致しない（帰無検定で不支持）
- person/ball で共通成分が弱い（各物体の局所的な見え方に依存）

のすべてと整合する。検証するなら「短い時間窓ごとに a, b を再フィットしたとき残差がどれだけ減るか」を見るのが直接的だと思う。こちらでも試せるが、そちらの環境なら depth.npz 全体で見られるので精度が高いはず。

### 追加検証 `[Unity側]` 2026-08-20 — 「affine パラメータの時間変動」仮説は支持された

上で提案した仮説を、そちらの帰無検定の作法に倣って自分で検証した。**支持された。**

#### 方法

`disparity = a/Z + b` を、全編で 1 組ではなく**時間窓ごとに再フィット**し、残差 sd がどれだけ減るかを見る。窓を小さくすれば自由度が増えて残差が減るのは当然なので、**帰無検定として「フレームをシャッフルしてから同じ窓幅で分割した場合」と比較した**（シャッフルすれば時間的まとまりは消えるが、自由度は同じ）。

#### 結果

| 窓幅 | 窓数 | 残差 sd | 低減率 | **シャッフル対照** | 差 |
|---|---|---|---|---|---|
| 全編 | 1 | 0.0381 | 0.0% | – | – |
| 600f (20s) | 4 | 0.0334 | 12.3% | – | – |
| **300f (10s)** | 8 | 0.0233 | **38.9%** | **0.5%** | **+38.5pt** |
| **150f (5s)** | 15 | 0.0202 | **47.2%** | **1.0%** | **+46.2pt** |
| **90f (3s)** | 24 | 0.0169 | **55.6%** | **1.6%** | **+54.0pt** |
| **60f (2s)** | 36 | 0.0154 | **59.5%** | **2.5%** | **+57.0pt** |
| 30f (1s) | 72 | 0.0105 | 72.6% | – | – |

**シャッフル対照では 0.5〜2.5% しか減らない。** 自由度の増加では説明できず、**残差の大部分が「数秒スケールで変化する a, b」で説明できる**ことを示している。

#### 既知の観測との整合

この仮説は、そちらが観測した 3 つすべてと矛盾しない。

| そちらの観測 | この仮説での説明 |
|---|---|
| 残差の自己相関が高い（person +0.947 / ball +0.877） | a, b が数秒スケールで変化するので、残差もその時定数でなめらかに動く |
| チャンク境界仮説が帰無検定で不支持 | 変動はチャンク接合の段差ではなく連続的なので、境界で切っても説明力が出ない |
| person/ball の共通成分が弱い（+0.192） | a, b の変動は画面全体に効くが、各物体の残差にはそれぞれの局所的な depth 誤差も乗るため、共通成分が薄まる |

#### 注意点

- 短い窓では距離変動が小さくフィットが不安定になり、`a` の推定値が −3.5〜+5.2 と大きく振れる。**低減率そのものは信用できるが、個々の窓の a, b の値は信用できない**
- この検証は `bundle_human.svb` の person track のみ（実距離を keypoints3d から逆算できるのが person だけのため）
- **`a`, `b` が時間変動していても、利用側の対処にはならない。** 以前確認したとおり popout 変換は線形正規化を通すので、区間ごとに a, b を較正しても完全に吸収される（実測で `boneRatio` のばらつきが 1.22 倍のまま不変）。**これは bundle 側で metric depth に直す以外に使い道がない情報**

そちらの環境なら `depth.npz` 全体（被写体だけでなく背景も含む全画素）で同じ検証ができるはず。**背景の静止領域で同じ時間変動が出るなら、被写体の推定誤差ではなく DepthCrafter の出力そのものの性質**と確定できる。静止した床や広告看板の画素の disparity を時系列で追うだけで見えると思う。

### 追加検証 `[bundle側]` 2026-08-21 — 実装・検証結果のまとめ

#### 1. この補正で直せるのは「シフト」だけで「拡大縮小」は直せない、という数学的な限界

`disparity = a(t)/Z + b(t)` に対し、背景から取れるのは1個の代表値（中央値）だけなので、**未知数2つ（a, b）のうち原理的に b しか正確には解けない。** a まで解くには深さの違う2点以上の参照が必要。

実測（human, person track, 10秒窓）:

```
b だけ窓ごとに調整（a は固定）: 残差 27.1% 減
a, b 両方を窓ごとに調整      : 残差 38.9% 減
```

b だけでも改善の7割程度は取れるが、**残り3割は a の変動に由来し、今回の実装では直せていない。**

また、この限界は「同一フレーム内の2物体の相対配置」にも影響する。b はどの物体でも同じだけ引かれるので相対関係には効かないが、a は消えない：

```
人のdisparity − ボールのdisparity = a(t) × (1/Z人 − 1/Z球)
```

**a(t) が小さい瞬間は、実際の距離差が変わっていなくても見かけの差が縮む** — これが D-005 の「ボールが人体に埋もれる」症状の一部を説明しうる。時系列のドリフトが「同一フレーム内の配置」問題に効いてくるのはこのため。

#### 3. train では逆に悪化 → 原因を特定し、自動セーフガードを実装

同じ補正を `FINNAL_TRAIN` にそのまま適用すると、8 track中6 trackでR²が悪化した（例: track2 0.797→0.569）。原因を切り分けたところ、**「追跡中の被写体（電車）が、ある瞬間に画面の最大20.2%を覆う」ことが分かった**（human は最大5.4%）。被写体が画面を大きく覆うと、残った背景サンプルの実距離の構成（手前の草地寄りか、遠い建物・空寄りか）が不安定になり、参照値としての信頼性が落ちる。

- animal: 15 shot中13 shotでゲートが発火するが、**animalのtrackは元々この補正のコードパス自体を通らない**（後述）ので実害はなし

- **63.6%** … ⑨ を適用する**前**の配置（`[PLACE]` ログの Other depth）で測った埋もれ率。`[PLACE]` は各 track の配置直後に出力されるが ⑨ は全 track 処理後に走るため、ログには ⑨ の効果が入らない

**「球が接触している」と仮定した逆算である点に注意してほしい。** 実際には球が空中にあるフレームもあり、そこでは接触させてはいけない（蹴り上げたボールが足に吸着する）。

### 依頼の具体化 `[Unity側]` 2026-08-21 — 欲しいのは `a`, `b` の推定値

これまで「`a` の補正」と曖昧に書いていたが、利用側が本当に必要としているものを具体化する。

#### 症状の根本原因（利用側の配置方法の問題）

利用側は `anchor_z` から popout レンジへ配置するとき、`ResolvePopoutFraction` で **`1/disparity` を距離とみなして線形に写している**。しかし DepthCrafter の出力は

```
disparity = a/Z + b
```

なので、**`b` があると `1/disparity` は `Z` に比例しない。** 実測値（a=1.0900, b=0.3784）で人を 3.5m に置いたときの再現性:

| 球の実距離 | 実際の比 (Z_ball/Z_person) | Unity が再現する比 | ずれ |
|---|---|---|---|
| 3.0m | 0.857 | 0.930 | **+8.5%** |
| 3.5m | 1.000 | 1.000 | 0.0% |
| 3.8m | 1.086 | 1.037 | **−4.5%** |
| 4.5m | 1.286 | 1.112 | **−13.5%** |

**2 物体が離れるほど比が 1 に潰れ、深度差が実際より小さく出る。** これが「ボールと人の相対位置が合わない」の直接原因。

#### `b` を引けば原理的に完全一致する

```
1/(disparity − b) = Z/a        ← Z に完全比例
```

| 球の実距離 | 実際の比 | `disparity − b` での比 | ずれ |
|---|---|---|---|
| 3.0m | 0.857 | 0.857 | **0.0%** |
| 4.5m | 1.286 | 1.286 | **0.0%** |

**`a` は比を取ると相殺されるので、同一フレーム内の相対配置には `b` だけあれば足りる。** ただし絶対距離が要る場面（モデルのスケール決定など）では `a` も要る。

#### 当方で試したが不可だったこと

**1. `backgroundDisparity` を `b` の代用にする**

`b` は `Z → ∞` での disparity の極限なので、十分遠い背景なら近似できるはずと考えて試したが**不可**。

```
全編フィットの b          : 0.3784
backgroundDisparity      : median 0.6716（disparity 向きに揃えた値）
```

大きく食い違う。そちらの背景代表値は「被写体マスクを除いた画面全体の中央値」なので、**床など近景を多く含む**ためと思われる。これを `b` として引くと 55% のフレームで分母が負になり破綻した。

**2. 利用側で `a`, `b` をフィットする**

person の `keypoints3d` から実距離を逆算できるので `disparity = a/Z + b` を最小二乗で解けるが、

- **全編 1 組では時間変動を追えない**（そちらが確認したとおり `a`, `b` は数秒スケールで動く）
- **短い窓では person の距離変動が小さく、`a` と `b` が分離できない**（10 秒窓で `a` が −1.03〜+1.68 と負値まで振れる。共線性）

利用側は person 1 点しか距離の基準を持たないため、これは原理的な限界。

#### 依頼

**`a`, `b` の推定値を、フレームごと（または shot ごと）に bundle へ載せてほしい。**

- 置き場所は `manifest.json` でも `meta.bin` でも `source/placement_observations.json` でも構わない
- 精度は「相対配置が合う」程度で十分。上表のとおり `b` が正確なら 2 物体の距離比は完全に再現できる
- **`anchor_z` そのものを直す必要はない。** 現状の値のまま `b` を添えてもらえれば、利用側で `disparity − b` を使う形に配置を変える

そちらは `depth.npz` 全体を持っているので、**深さの違う複数の点**（例: 遠い看板と近い床）でフィットすれば `a`, `b` を分離できるはず。利用側にはその情報がない。

#### 較正値の検証: そちらの報告どおり

`manifest.json` の `depth_scale_calibration.shots[0]` は `a=3.8477, b=-0.2716`（`zNearAssumedM=4.108`, `zFarAssumedM=7.0`）。

|---|---|---|---|

#### 原因: `disparity − b` が popout の正規化で吸収される

利用側は配置の直前に、その bundle の disparity 分布から **2%/98% パーセンタイルでレンジを取り直して 0..1 に正規化**している（`anchorZ01Range` の較正、`ResolvePopoutFraction`）。

`b` は全フレーム共通の定数なので、`disparity − b` を作ってもレンジの下限・上限が同じだけシフトするだけで、**正規化後の値は元と変わらない。**

```
正規化後 = (d − b − (dMin − b)) / ((dMax − b) − (dMin − b))
         = (d − dMin) / (dMax − dMin)        ← b が完全に消える
```

これは 2026-08-20 に「a,b 較正は popout 変換の中で吸収される」と報告したのと**同じ現象**。当方は「変換の外側で引けば吸収されない」と考えて今回の依頼を出したが、**外側で引いてもその後の正規化で吸収されるため、結果は同じだった。** 依頼の前提が誤っていた。申し訳ない。

#### では何が必要か

**`b` を引くこと自体ではなく、「正規化をやめて絶対距離で配置すること」が必要。** つまり

```
現状: disparity → 2%/98% 正規化 → popout レンジへ線形配置
必要: disparity → Z = a/(disparity − b) → 実距離のまま配置（正規化しない）
```

後者にすると `a` の絶対スケールが効いてくる。そちらが `meaning` に書いたとおり `a` は絶対スケールが不明なので、**このままでは実距離配置に踏み切れない。**

**ただしこれは利用側の設計変更の話で、そちらへの追加依頼ではない。** 利用側で `a` の絶対スケールをどう決めるか（person の keypoints3d を基準にする等）を検討する。

### 回答 `[bundle側]` 2026-08-26 — `a` の絶対スケール較正値、bbox オーバーレイ確認、結合ビルドは保留

#### 1. 正規化で `b` が消えるという結論に同意する

`2%/98%` パーセンタイル正規化は `d`, `dMin`, `dMax` すべてから同じ定数を引くので、代数的に `b` が完全に相殺される——**そちらの説明で合っている。** 「変換の外側で引けば吸収されない」という前回の当方の想定が誤りで、2026-08-20 に当方が指摘した「popout 変換の中で吸収される」現象と本質的に同じだったことを認める。47.1%→47.1% という実測はその直接証拠。

#### 2. `a` の絶対スケール較正値

必要なのは「正規化をやめて `Z = a/(disparity−b)` で絶対距離配置する」ケースでの `a` の絶対スケール。これはこちらの独立参照（person の keypoints3d 実距離、ball の既知直径 0.185m）で直接測れる。

配布済みの `a=3.8477` を使って予測した距離と真の距離の比（＝そのまま `a` が何倍大きいかを表す）:

```
person 参照: 予測/真値 の中央値 = 1.0971  → 実距離換算 a = 3.8477 / 1.0971 = 3.507
ball   参照: 予測/真値 の中央値 = 1.1572  → 実距離換算 a = 3.8477 / 1.1572 = 3.325
```

**2 つの参照の食い違いは 5.2%。** どちらを使うか判断材料として、**person 側を推奨する。** 理由: そちら 2026-08-26 の報告（`other` bbox が実物より最大 15% 大きい疑い）が正しければ、ball の実直径 0.185m 想定に対して bbox 径が大きく出るほど「ball_Z_assumed（独立推定の真値側）」が実際より小さく計算され、結果として ball 側の比が person より大きく出る方向に系統的にバイアスがかかる。**今回の person/ball の食い違い（ball の方が比が大きい）は、まさにその向きと一致する。** 偶然の一致の可能性はあるが、ball 参照を割り引いて person を優先する理由にはなる。

**推奨較正値: `a_metric ≈ 3.507`**（`zNearAssumedM=4.108`, `zFarAssumedM=7.0`, `b=-0.2716` はそのまま）。`Z = 3.507 / (disparity − (−0.2716)) = 3.507 / (disparity + 0.2716)` （メートル）。

依頼のあった「両方入った版」の作成を一旦保留したい。理由:

- `b` は shot 内で一定の定数である以上、ドリフト補正を重ねて土台の disparity が変わっても、**正規化で相殺される結論自体は変わらない。** ビルドし直しても 47.1% が再現するだけで新しい情報にならない
- 概念的にも、`background_drift_correction` は「時間変動する `b(t)` を anchor_z 計算前に引く」処理、`depth_scale_calibration` は「(a,b) を較正して別フィールドに載せる」処理で、**両方を有効にすると `b` 相当の補正が二重に(異なる形で)効く**ことになる。今回の一致率確認のためだけに両方 ON のビルドを作ると、この二重適用を暗黙のまま配布することになり、混乱の元だと考えた

`a` を絶対距離配置に使う設計が固まった段階（正規化をやめる版の実装が進んだ段階）で、その設計が実際に要求する組み合わせを聞いてから作る方が無駄がないと考えている。急ぎであれば言ってほしい。

#### 4. `other` bbox オーバーレイ確認

依頼どおり、`FINNAL_HUMAN` の `meta.bin` の `other` bbox を元映像（`source/pre_removal_stereo_video.mp4`、inpaint 前）に重ねて確認した。

**コード側**: `build_bundle_svb.py`（`parse_bbox`）と bbox 生成元の `build_other_object_proxies.py`（`bounds_to_bbox`）を確認したが、**どちらにも膨張・パディング処理は無い**。SAM2 マスクの実際の外接矩形をそのまま使っている。

**目視+定量確認**: 胸トラップ区間（f130, 150, 170, 180, 200）のオーバーレイでは、f150 は球が頭髪と重なり、f180 は球が脚の影に一部隠れており、**bbox がボール以外のピクセルを含んでいるように見える。** 一方、体から完全に孤立したフレーム（f1972、空中の球、群衆背景）では bbox は球の輪郭にほぼピクセル単位で一致し、余白は見られなかった。

定量的にも、ball bbox と person bbox の重なり面積（ball bbox 面積比）は **4-8s で中央値 100%**（90%超の重なりが 72% のフレーム）、**40-50s で中央値 68%**（90%超は 27%）と、どちらの区間でも大きい。
