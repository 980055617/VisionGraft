# Animal モデルを差し替えても同じ見た目にする

目標: **どのモデルに変えても、映像の動物とおおよそ同じ大きさ・同じ姿勢で置かれること**
（2026-09-05 ユーザー要望）。

配置パイプライン全体は [bundle-placement.md](bundle-placement.md)、
姿勢は [smpl-retargeting.md](smpl-retargeting.md) を見ること。

## この文書の読み方

1. [結論](#この項の結論2026-09-06) — 何ができて何ができないか
2. [そもそも一致しない理由](#そもそもモデルは完全には一致しない2026-09-06) — 5 つの理由
3. [姿勢が揃わない仕組み](#姿勢が揃わない理由こちらが本題) — 原因と、試して失敗した 3 方式
4. 以降は参考データ（大きさ・スケール・欠損ボーン・道具）

**この文書の変更提案は全て却下されている。コードは元の状態のまま。**
残っているのは診断ツールと記録だけ。

## この項の結論（2026-09-06）

姿勢をモデル間で揃える試みは 3 通り試して**すべて却下**された。

| 方式 | 数値 | 絵 | 状態 |
|---|---|---|---|
| 絶対姿勢（jointFrameMap 差し替え）| 膝の幅 103°→0° | 四肢が破綻 | OFF |
| bind を基準（27_GermanShepherd）へ揃える | 膝角 59〜60° に一致 | メッシュがねじれる | OFF |
| bind の開き角に上限 60° | 犬は無変更 | 触ったモデルが変形 | OFF |

**共通の原因は 1 つ**: スキンはそのモデル自身の bind pose に対して張られているので、
ボーンを bind から大きく回すとメッシュが変形する。
そして**直したいモデルほど大きく回す必要がある**ので、直せない。

**コードでできることは無い。**この方向を進めるなら asset 側
（各リグの bind pose を作り直してスキンを張り直す）になる。

## そもそもモデルは完全には一致しない（2026-09-06）

「なぜモデルごとに違うのか、一緒にはできないのか」への回答。理由は 4 つある。

### 1. 姿勢データが「絶対」ではなく「差分」

`meta.bin` の SMAL `body_pose` は「SMAL の rest から何度曲げるか」であって
「膝を何度にせよ」ではない。だから **結果 = そのモデルの rest + 差分**。
モデルの rest（bind pose）は作者ごとに違い、膝で 27°〜156° の幅がある。

### 2. 揃えること自体は技術的にできる（実証済み）

絶対姿勢に変えたら膝のモデル間の幅は 103° → **0°** になった。
つまり「同じにする」ことは可能。

### 3. しかし揃えると見た目が悪くなる

- **SMAL の rest は立ち姿ではない。**揃えると全モデルが中腰になる
  （実測 54〜68°。ユーザー判定「前の方が足が普通に見える」）
- **bind pose には作者の解剖学的な作り込みが入っている。**
  犬の 48° は「立っている犬の膝」であって、捨てると立ち姿でなくなる

### 4. 関節角を揃えても見た目は一致しない。体つきが違うから

スケールに依らない比（前脚の長さ ÷ 胴の長さ）:

| モデル | 前脚長 ÷ 胴長 |
|---|---:|
| 33_Hare | **2.36** |
| 49_Rabbit | 1.30 |
| 00_Dog | 1.03 |
| 40_Mammoth | 0.95 |
| 08_Bear1.0 | 0.79 |
| 05_Horse | 0.72 |
| 36_LabradorDog | 0.61 |
| 13_Bloodhund | 0.59 |
| 27_GermanShepherd | 0.58 |
| 11_Beaver | 0.57 |

全 48 モデルで中央 0.61、範囲 0.31〜2.36 の **7.5 倍**。
Hare は Bloodhund の 4 倍脚が長い。**同じ関節角を当てても骨の長さが違えば形は一致しない。**
これは動物の個性そのものなので、消すべきものでもない。

### 5. 映像が拘束していない区間がある

`bundle_animal` の shot3（f151〜258）は頭のクローズアップで、**後ろ足が映っていない**。
bbox も keypoint も脚を拘束しないので、この区間の脚は bind pose 次第になる。
**bundle に情報が無い**ので、FK をどう作っても決まらない。

### 試して失敗した対処: bind pose を共通の基準へ揃える（2026-09-06、既定 OFF）

「body_pose が差分なら、bind を先に揃えてしまえばよい」という案（ユーザー提案）。
**発想は正しく、SMAL rest を基準にした前回の失敗とは別物**（回転の計算は触らず、
静的な前処理として rest 方向だけ差し替えるので、連鎖が壊れる問題は起きない）。

実装: 各モデルの rest 方向を **27_GermanShepherd から採取した基準テーブル**（10 関節、
366 サンプルでぶれ 0.0000）へ回してから差分を当てる。
基準に立ち姿のモデルを選んだので、SMAL rest を基準にしたときの「全員中腰」は起きない。

結果: 基準モデル自身は変化 0.00%、他は 3〜7% 変化し、膝角は
Bloodhund 60.0° / Hare 59.0° / Labrador 59.5° とほぼ一致した。

**しかし絵ではメッシュが激しくねじれた**（ユーザー判定「めっちゃねじれている」）。

#### ロールは主因ではなかった

最初はロールを基準に合わせていたのが原因と考え、方向だけを `FromToRotation`
（回転軸が両者に垂直＝ねじれを足さない最小回転）で合わせる版に変えた。
**結果はほぼ同じ**（画素の変化 3.16% → 3.15%、6.76% → 6.84%）。

#### 主因はスキニングそのもの。runtime では原理的にできない

スキンは**そのモデル自身の bind pose に対して**張られている。
ボーンを bind から大きく回せばメッシュはその分だけ変形する。これは仕様。

基準へ揃えるのに必要な回転量は実測で **34〜140°**
（49_Rabbit は joint 17 が 100.5°、joint 21 が 105.8°）。
そこまで回せば必ず崩れる。

**この方向でやるなら asset 側**（各リグの bind pose を作り直してスキンを張り直す）
でしかできない。モデリング作業であってコードの仕事ではない。

コードは `normalizeBindPoseToCanonical`（既定 OFF、`-canonBind` で A/B）として残した。
比較画像は `docs/tmp/roll_compare.png`（何もしない / ロールも揃える / 方向だけ）。

### 結論: 目標は「全部同じ」ではなく「どれも壊れて見えない」

壊れていたのは極端な外れ値だけ（bind 膝が 78°〜156° の 8 モデル）。
残り 44 モデルは元から妥当だった。上限クランプはその 8 つだけを直し、
残りは 1 画素も変えない。

## 姿勢が揃わない理由（こちらが本題）

### 実測: 同じ SMAL 姿勢なのに膝の曲がりが 103° 違う

全モデルは `meta.bin` の同じ SMAL `body_pose` を受け取る。正しく伝われば膝の曲がりは
モデル間で一致するはず。同一フレームで 8 モデルを比べた（`[ANIMALANG]`、
`Vector3.Angle(lo-up, paw-lo)` = **まっすぐからのズレ**。0° が直線）。

```
frame  shot  00_Dog Bear1.0 Beaver Bloodhund GermanSh  Hare  Labrador Mammoth   幅
   25     1      35      35     35        35       35    35        35      35    0°   ← 差し替え前
   50     2      56      67    140        88       63   166        84      58  110°
   70     2      50      63    128        72       59   154        68      50  104°
```

**全 61 フレームでのモデル間の幅は中央 103°**（最大 126°）。

### 原因: FK は SMAL rest からの「差分」を bind pose に足しているだけ

`AnimalSmalFkApplier`:

```csharp
Quaternion bendSmal  = Quaternion.FromToRotation(smalRestDir, smalPosedDir);  // SMAL rest からの差分
Quaternion bendUnity = jointFrameMap * bendSmal * Inverse(jointFrameMap);     // Unity の枠へ写す
tw[joint] = bendUnity * restWorldRot;                                         // モデルの bind に掛ける
```

**絶対姿勢ではなく差分。**モデルの bind pose の曲がりはそのまま残る。

実行時の膝角を bind pose の膝角と突き合わせると **r² = 0.955、傾き 0.84**:

| モデル | bind の膝 | 実行時 | 差 |
|---|---:|---:|---:|
| 40_Mammoth | 30° | 46° | +16 |
| 00_Dog | 33° | 50° | +17 |
| 27_GermanShepherd | 44° | 60° | +16 |
| 36_LabradorDog | 48° | 46° | −3 |
| 08_Bear1.0 | 50° | 64° | +14 |
| 13_Bloodhund | 52° | 48° | −4 |
| 11_Beaver | 114° | 111° | −3 |
| 33_Hare | 149° | 146° | −4 |

**実行時の姿勢はほぼ bind pose で決まっている。**
SMAL が足す量（+14〜+17°）はコード内の実測基準（膝 rest 32.6° → 犬 46.9/54.1°、
つまり +14〜+21°）と一致するので、**transport の大きさは正しい**。
問題は起点が SMAL の rest ではなくモデルの bind であること。

### 試して失敗した対処: jointFrameMap をモデル共通の向きにする（2026-09-05、revert 済み）

`jointFrameMap` を「そのモデルの bind 方向」から「SMAL の rest 方向を `worldFk0` で
写したもの」に差し替え、結果のボーン方向を `worldFk0 * smalPosedDir` にする案。

```csharp
Vector3 targetDirWorld = (worldFk0 * smalPosedDir).normalized;
tw[joint] = Quaternion.FromToRotation(unityRestDirWorld, targetDirWorld) * restWorldRot;
```

**数値だけ見ると成功に見えた**が、絵で破綻していた（2026-09-05 ユーザー確認済み）。
比較画像は `docs/tmp/fk_before_after.png`。

**見た目の可否は実測値からは判定できない。必ず絵を出してユーザーに見てもらうこと。**
このときこちらが絵を見て勝手に revert したが、それは越権だった。

| | 修正前 | この案 |
|---|---:|---:|
| 膝のモデル間の幅（中央）| 103° | **0°** |
| 肘のモデル間の幅（中央）| 27° | **0°** |
| 各モデルの膝角 | 44〜144° | **全モデル 32°** |
| 見た目 | — | **四肢が伸びて破綻** |

全モデルが 32° に揃ったのは **SMAL の rest 膝角（32.6°）そのもの**で、
姿勢が当たったのではなく**曲げが失われて rest に潰れた**ということ。
**数値が揃ったことを成功と読んではいけない。必ず絵で確かめる。**

破綻した理由は 2 つあり、どちらもコード内のコメントが既に警告していた:

1. **SMAL の連鎖を累積していない。** `smalPosedDir = rawLocal * smalRestDir` は
   その関節の**親フレームでの**局所回転でしかない。root フレームでそのまま使うと
   親の曲げが乗らず、各ボーンが rest 方向を向くだけになる
2. **`FromToRotation` のロールが不定。** `unityRestDirWorld`（モデルの bind 方向）と
   `worldFk0 * smalRestDir` の角度は REST-CHECK 診断で 62〜83°（尻尾）、
   Lion では 95〜122° と実測されている。この角度で最小回転を取るとロールが
   任意に決まり、メッシュがねじれる。**per-joint の `jointFrameMap` はまさに
   これを避けるために存在する**

正しくやるなら (a) SMAL 空間で連鎖を累積した絶対回転を作り、
(b) ロールを拘束した基底で写す（`useTwoAxisJointFrameMap` が同じ問題への既存の対処、
ただし既定 OFF で未検証）必要がある。**1 行の差し替えでは済まない。**

### 試して失敗した対処: bind の開き角に上限を設ける（2026-09-05〜06、既定 OFF）

`AnimalSmalFkApplier.normalizeLimbBindAngleToSmalRest`（既定 true、`-limbNorm` で A/B）。
lower の 4 関節（SMAL joint 8 / 12 / 18 / 22）だけを対象に、
親（upper）と自分の rest 方向が作る面の法線を軸にして、両者のなす角を SMAL の rest 角へ合わせる。
**回すのは曲げ軸まわりの 1 自由度だけ**なのでロールに触らず、
jointFrameMap を差し替えたときのようなメッシュのねじれは起きない。

| | 修正前 | 対処 A |
|---|---:|---:|
| 膝のモデル間の幅（中央）| 103° | **29°** |
| 肘のモデル間の幅（中央）| 27° | **4°** |
| 33_Hare の膝 | 144° | 28° |
| 11_Beaver の膝 | 110° | 22° |
| 27_GermanShepherd の膝 | 60° | 51° |

補正量の実測: Hare −118°/−115°、Beaver −87°/−76°、LabradorDog −16°、GermanShepherd −12°。

**これも使えない（2026-09-06）。**上限内のモデルは 1 画素も変わらないので安全と考えたが、
**触るモデルでは崩れる**。49_Rabbit は 156°→60° で 96° 回すことになり、
後ろ足が伸びた棒状に変形した（`docs/tmp/clamp_49_Rabbit_before.png` と `_after.png`）。
基準揃えを壊したのと同じスキニングの問題で、回転量が同じなら結果も同じ。

**「犬は変わらないから安全」は触らないモデルについての話でしかなかった。**
変更を評価するときは、**変わらなかったものではなく変わったものを見ること。**

### 残った 2 クラスタの原因: 膝の折れる向きが逆のモデルが 18 ある

対処 A の後も 22〜28° と 48〜51° の 2 つに分かれた。曲げの**大きさ**は揃えたが
**向き**を揃えていなかったため、向きが逆のモデルでは SMAL の差分が加算ではなく減算になる。

体の前方（前脚の付け根 − 後脚の付け根）と world up から右方向を作り、
曲げ軸 `Cross(upperDir, lowerDir)` をそれに射影した符号（`kneeSign`）で判別できる。

| モデル | bind 膝 | kneeSign | 対処 A 後 |
|---|---:|---:|---:|
| 11_Beaver | 120° | −0.978 | 22° |
| 13_Bloodhund | 51° | −0.997 | 25° |
| 36_LabradorDog | 48° | −0.993 | 25° |
| 33_Hare | 151° | −0.686 | 28° |
| 08_Bear1.0 | 42° | +0.994 | 48° |
| 00_Dog | 33° | +1.000 | 50° |
| 40_Mammoth | 28° | +0.994 | 50° |
| 27_GermanShepherd | 44° | +0.999 | 51° |

**符号と結果が完全に対応している。**全 52 モデルでは正 30 / 負 18
（脚ボーンを持たない 4 モデルは測定不能）。

### Beaver の絵が変わらなかった理由

膝角は 110° → 22° と大きく動いたのに、画素の変化は 0.7% しかなかった。
**後ろ足が体の下に隠れていて、見えているのは足先だけ**だったため

**姿勢の変更を絵で確かめるときは、その部位が見えているモデルを選ぶこと。**

## 上限クランプについての実測（2026-09-06）

「bind の 60° 上限は妥当か。実行時に 60° を超えることはあるか」への回答。

**クランプは bind（基準姿勢）にしか掛からない。実行時は普通に超える。**

| モデル | 実行時の膝角 | 60° 超のフレーム |
|---|---|---:|
| 36_LabradorDog（対象外・bind 48°）| 14〜88° | 31% |
| 33_Hare（対象・bind 151°→60°）| 26〜92° | 34% |

shot ごとに見ると shot2（座っている犬）で最大になる
（Labrador 66〜88°・中央 76°、Hare 70〜92°・中央 80°）。座り姿勢は正しく出ている。

つまり上限は実行時の可動域を狭めない。問題は上限そのものではなく、
**bind を動かすとメッシュが変形すること**（上記）。

## 実測: 見かけの大きさはおおよそ揃っている

**先に結論。**差し替えで大きく変わるのは大きさではない。

同じ動画・同じフレーム（bundle_animal、f=40〜320 の共通 55 フレーム）で 8 モデルを
入れ替えて `sizeRatio`（投影 AABB 高 ÷ bbox 高 = 画面上の見かけの大きさ）を測った。

| モデル | sizeRatio | boneRatio |
|---|---:|---:|
| 11_Beaver | 0.986 | 0.986 |
| 36_LabradorDog | 1.043 | 1.042 |
| 27_GermanShepherd | 1.074 | 1.106 |
| 00_Dog | 1.157 | 1.015 |
| 13_Bloodhund | 1.167 | 1.231 |
| 40_Mammoth | 1.294 | 1.048 |
| 33_Hare | 1.357 | 1.063 |
| 08_Bear1.0 | 1.410 | 1.109 |

- **全体の幅は 0.986〜1.410（1.43 倍）**。極端に形の違う 8 種を並べてこの幅
- **犬 4 種に限れば 1.043〜1.167（±6%）**。同種のモデルどうしはよく揃っている

⑨ `RefineLockedScaleFromProjectedBones` が shot 先頭で
「骨の投影スパン = bbox 高」に合わせ込む（boneRatio → 1.000）ので、
初期スケールがどう決まっても大きさは吸収される。

**つまり「モデルを変えると見た目が変わる」の主因は大きさではない。**
残る候補は姿勢（頭の向き・脚の曲がり）と、そもそも姿勢が当たらないモデルの存在。

### 外れた仮説: bodyShare（体 ÷ 骨スパン）で予測する

「⑨ が骨スパンを bbox に合わせるので、骨スパンに占める体の割合が見かけの大きさを決める」
と考えて `bodyShare = withers ÷ boneSpanY` を測ったところ、モデル間で 6.28 倍ばらついた。
**しかし実測と相関しなかった。**

| モデル | bodyShare の予測 | 実測 sizeRatio |
|---|---:|---:|
| 11_Beaver | ×0.28（最小）| 0.986 |
| 33_Hare | ×0.74 | **1.357** |
| 00_Dog | ×1.43 | 1.157 |
| 40_Mammoth | ×1.73（最大）| 1.294 |

`withers`（前脚の付け根〜前足）は脚の長さであって体の大きさではない。
**この指標で判断してはいけない。**判断は動画を回して `sizeRatio` を見ること。

## スケールの決まり方（参考）

### Animal の初期スケールは AABB の高さ、Human は骨格

`ReplaceableModel.CaptureSkeletonHeight` は `animator.isHuman` でしか動かない。
Animal は Generic リグなので `baseSkeletonHeightMeters = 0` になり、
`GetModelHeightMeters()` は AABB の高さを返す。

```
Animal: modelH=6.6894  aabbH=6.6894  skelH=0.0000   ← AABB 由来
Human : modelH=1.7346  aabbH=2.0428  skelH=1.7346   ← 骨格由来（AABB は 18% 大きい）
```

**ただしこの差は実害になっていない。**⑨ が shot 先頭で骨の投影スパンを bbox に
合わせ込むので、初期値の違いは吸収される（上の実測どおり）。

### 00_Dog だけ投影ボーンの選び方が違う

`ResolveProjectionBones` は SkinnedMeshRenderer のボーン配列を使うが、
**00_Dog は MeshRenderer 22 個構成で SkinnedMeshRenderer を持たない**ため、
フォールバック経路（Renderer の transform 位置）に落ちる。
`[PLACE]` の `topBone=er.R bottomBone=arm.003.R` はボーン名ではなく
**メッシュ部品の名前**で、経路が違うことがログから確認できる。

**これも見かけの大きさとしては実害が出ていない**（00_Dog の sizeRatio 1.157 は
他の犬 1.043〜1.167 の範囲内）。測り方が他と違う点は残るので、
今後の不整合の候補として記録しておく。

## refH（手動の高さ指定）は全モデル未使用

`ReplaceableModel.referenceHeightMeters` を設定すると AABB の代わりにその値が使われるが、

（`bodyShare` の最大/最小が 6.28 倍 → 174 倍に悪化。174 倍は脚ボーンを持たない
4 モデルでスパンが潰れるため）。四足だけに限れば 6.2 倍 → 4.2 倍だが決定打ではない。

## 頭の向きがモデルごとに違う（2026-09-06、#4 の調査）

### 原因: 頭は body_pose で駆動されていない

`SmalRestDirByJoint` にあるのは joint **7 / 8 / 11 / 12 / 15 / 17 / 18 / 21 / 22 / 25 / 26** だけ。
**joint 16（頭）が無い**ので、頭は `tw[joint] = parentTW * bindLoc` の分岐に落ちる。
つまり **首に付いて動くだけで、頭自身の回転は一切当たらない**。
頭の向きはモデルの bind pose が決めるので、bind で傾いている・下を向いているモデルは
何を再生してもそのまま。CLAUDE.md に既知の制限として書かれているとおり。

理由は「頭には aim-child が無く、Unity 側の rest 方向を導出できない」（ADR-0001/0002）。

### データには頭の動きが入っている（捨てられている）

`body_pose` の各関節が rest からどれだけ回っているかを実測した
（bundle_animal、40 秒、808 サンプル）。

| joint | 部位 | 中央 | p90 | 最大 | 駆動 |
|---|---|---:|---:|---:|---|
| 15 | 首 | 31.6° | 44.2° | 63.2° | あり |
| **16** | **頭** | **22.4°** | **32.0°** | **49.2°** | **なし** |
| 9 / 13 | 前足 paw | 14.9° / 16.3° | | | なし |
| 19 / 23 | 後足 paw | 12.1° / 11.3° | | | なし |
| 33 / 34 | 耳 | 26.4° / 18.3° | | | なし |
| 32 | 口 | 5.3° | | | なし |

**頭は中央 22.4° 動いているのに全部捨てている。**首（31.6°）に次ぐ大きさ。

### #3 と違って bind の壁には当たらない

頭を駆動するのは「bind に差分を足す」だけなので、**bind pose を大きく回す必要がない**。
#3 で全方式を潰した「スキンが bind に張られているので大きく回すと崩れる」問題は起きない。

必要なのは joint 16 の rest 方向 2 つ:

- **SMAL 側**: SMAL の rest skeleton で 16 の子は 32（口）。`Docs/smal-rest-skeleton.json` から
  head→mouth 方向を取れる（他の関節と同じ作り方）
- **Unity 側**: 正規リグに口ボーンは無いが、`TryGetBoneCenterDirectionWorld` が使っている
  **頭ボーン → 頭のメッシュ重心**が rig 非依存の方向として使える

### 注意: `[ANIMALKP]` の `Head=` は使えない

値は**画素ではなく角度（度）**。しかも全区間で 86〜89° とほぼ一定で、
追従の誤差ではなく診断側の定義のずれ（頭ボーンの方向 vs 「頭→鼻先端」の keypoint 方向）。
**この数字を頭の誤差として読まないこと。**

## 頭が斜めを向くモデルの補正（2026-09-06、採用）

### 症状

`45_MountainGoat`（実機の animal で選択中）の頭が常に斜めを向く。
モデルの bind pose に横向きが入っており、body_pose は差分なので消えない。

### 測るのは「首→頭の位置」ではなく「顔の向き」

頭ボーンの子（`Nose` / `Jaw` / `Mouth`）があればそれで測る。位置で測ると
頭ボーン自身の向きのずれが残る。

| モデル | 首→頭の位置 | 頭→鼻の向き | 位置基準の誤差 |
|---|---:|---:|---:|
| 45_MountainGoat | −41° | **−50°** | 9° 足りない |
| 38_LionessV2 | −38° | **−52°** | 14° 足りない |
| 34_Hyena | −25° | **−49°** | 24° 足りない |
| 16_Deer1 | −12° | **−4°** | **8° 行き過ぎ** |

鼻・顎・口のボーンを持つのは 48 モデル中 19。無いモデルは首→頭に落とす。

### **頭 1 本で回すと首が潰れる。首の鎖に分散すること**

最初は頭ボーン 1 本で −50° 回した。結果、首の付け根から頭にかけて
**一箇所で急に折れ、喉が潰れて段差になった**（ユーザー指摘「首がぐにゅってなっている」）。

理由は 2 つ:

1. **スキニングは「1 関節あたりの曲がり」で決まる。**関節をまたぐ頂点は両側の
   ボーンの向きを混ぜて動くので、短い区間で 50° を吸収させると潰れる。
   ヤギの首は `Neck1 / Neck2 / neck / head` の 4 本あり、分散すれば
   **1 関節あたり 12.6°** に下がり、回転が首全体の長さに広がる
2. **補正を FK の中で毎フレーム掛けると、bind 情報が半端になる。**
   `restWorldRot` と `unityRestDirWorld` だけを後から回していたが、
   FK は `bindRotLocal` / `bindRotWorld` / `bindDirLocal` も使う。
   特に足先・尻尾が通る `tw = parentTW * bindLoc` の経路は補正を知らないので、
   **補正済みの首と補正なしの前提が混ざる**

### 対処: bind 採取の前に首の鎖へ焼き込む

`AnimalPoseApplier.CaptureBindHeadYaw` は `PrimeAnimalBinds` より前に走る。
ここで首の鎖（`head` から `neck`、さらに名前に neck を含む親）を集め、
`-bindHeadYaw / 本数` ずつ親から順に回す。以後に採取される bind は全部補正済みになり、
**FK 側の特殊分岐は不要**（実装したものを撤去した）。

適用範囲は 10°〜60°。10° 未満は誤差、60° 超は `48_Puma`（179°）のように
リグの軸の取り方が特殊で測定が破綻するモデルを巻き込まないため。
対象は 7 モデル（33_Hare / 45_MountainGoat / 38_LionessV2 / 34_Hyena /
16_Deer1 / 02_WildBoar / 11_Beaver）。

比較画像: `docs/tmp/goat_neckchain.png`（補正なし / 頭 1 本 / 首 4 本に分散）。
