## 1. 姿勢一致: 2 つの基準点取り違えを修正して完了

### 発端

⑨⑩（Else の深度補正）が「keypoints ベースの試算では効くのに、実ボーンで実装すると効かない」という失敗を 2 回繰り返した。ユーザーから **「実モデルが keypoint ほど曲がっていないのが原因では」** という指摘があり、`[BONEKP]` ログ（実ボーンと keypoints3d の投影位置の差）を新設して初めて両者を直接比較した。**これまで一度も測っていなかった量。**

### 見つかった取り違え 2 件

| # | 取り違え | 影響 |
|---|---|---|
| 1 | **測定側**: `[BONEKP]` で Unity の Foot ボーンを keypoints の Ankle と比較していた | Foot ボーンは実際には **Heel** の位置（Foot vs Heel −2.5px、Foot vs Ankle +13.6px）。別々の点を比べていた |
| 2 | **コード側**: `sourceShin` が「膝→足首」、モデル側 `ResolveBoneDistance(LowerLeg, Foot)` が「膝→踵」 | **別区間で骨長比を計算**していた。倍率が系統的にずれる |

2 は `sourceShin` を「膝→踵」に変更して修正（`HumanSourceKeypointRightHeel`/`LeftHeel` を追加）。

### 結果: 骨長補正を OFF にすると足・手首がほぼ完全一致

定義を揃えたうえで `enableHumanBoneLengthCorrection` の ON/OFF を比較した。

| 部位 | 補正 ON | **補正 OFF** |
|---|---|---|
| 右足 | +17.5px | **0.0px** |
| 左足 | +11.2px | **−1.9px** |
| 右手首 | −5.7px | **−0.6px** |
| 左手首 | −8.3px | **−0.9px** |
| 右膝 | +3.7px | +10.3px ← 膝だけ ON が良い |
| **RMS median** | 6.35% | **5.85%** |

**「膝を 10px 合わせるために足を 17px・手首を 8px ずらす」割の合わないトレードオフ**だった。`enableHumanBoneLengthCorrection` を**既定 OFF に変更**。実機でも「（keypoints に）近づいていそう」と確認済み。

2026-08-06 当時の前提（足首が bbox 高さの 10% *上* にずれる）は既に成立していない。⑧ の深度補正で遠近感が正しくなったこと、bundle 側の depth 修正が進んだことで状況が変わり、**補正だけが当時の前提のまま残っていた。**

### AimAt は必須と再確認

| 設定 | RMS median | p90 |
|---|---|---|
| **AimAt ON / 骨長 OFF（現在）** | **5.85%** | 9.47% |

## 3. bundle 側の `a`,`b` 較正値を検証

### 依頼の経緯

「ボールと人の相対位置が合わない」原因を、**Unity が `1/disparity` を距離とみなして配置している**ことと特定した。`disparity = a/Z + b` の `b` があると `1/disparity` は `Z` に比例しない。

実測（a=1.09, b=0.378）で人を 3.5m に置いたときの再現性:

| 球の実距離 | 実際の比 | Unity が再現する比 | ずれ |
|---|---|---|---|
| 3.0m | 0.857 | 0.930 | +8.5% |
| 4.5m | 1.286 | 1.112 | **−13.5%** |

これを受けて「`a`,`b` の推定値を bundle に載せてほしい」と依頼した。

### bundle 側の対応

静止した背景パッチ 2 点（近い 4.108m / 遠い 7.0m）から shot ごとに `a`,`b` を解き、`bundle_shots_depthscale_test.svb` として配布。`manifest.json` の `depth_scale_calibration` に格納（`anchor_z` は無変更）。

bundle 側は途中 2 回失敗しており（person を参照点に使うと発散、遠い点の距離を全体フィットから逆算すると負値）、その経緯も含めて報告してくれた。

### 検証結果: 較正は正しい。しかし配置は変わらなかった

**較正値の再現性:**

```
a=3.8477  b=-0.2716
person の実距離を予測 → 誤差 median +9.7%、CV 0.090
（bundle 側の報告値 0.089 と一致）
```

**独立に再現できた。** なお当方が person の全体フィットから出していた `b` は **+0.51 で符号が逆**だった。person 1 点では共線性で不安定になるという bundle 側の指摘どおり。

**配置への効果:**

| 方式 | 全編 埋もれ | 4-8s 埋もれ |
|---|---|---|
| `b` を引かない | 21.6% | **47.1%** |
| そちらの `b` = −0.2716 | 22.5% | **47.1%** |

**4-8 秒は完全に不変。**

### 原因: 依頼の前提そのものが誤っていた

利用側は配置直前に **2%/98% パーセンタイルでレンジを取り直して正規化**している。`b` は全フレーム共通の定数なので、

```
(d − b − (dMin − b)) / ((dMax − b) − (dMin − b)) = (d − dMin) / (dMax − dMin)
```

**`b` が完全に消える。** 2026-08-20 に「popout 変換の中で吸収される」と報告したのと同じ現象で、「変換の外側で引けば吸収されない」という当方の読みが誤りだった。

### 本当に必要なもの

```
現状: disparity → 2%/98% 正規化 → popout レンジへ線形配置
必要: disparity → Z = a/(disparity − b) → 実距離のまま配置（正規化しない）
```

**正規化をやめて絶対距離で配置する**という設計変更が要る。これには `a` の絶対スケールが必要だが、bundle 側も「`a` は絶対スケール不明」としている。**次週の検討事項。**

## 今週の検証手法の反省

**同じ失敗を 3 回繰り返した。** いずれも「試算では効くはず → 実装 → 実機で効かない」。

| 回 | 実装 | 誤りの所在 |
|---|---|---|
| 1 | ⑩ めり込み解消 | 試算 keypoints / 実装 実ボーン |
| 2 | ⑨ 実距離の比 | 同上 + `[PLACE]` ログで効果を測れない |
| 3 | `b` を引く依頼 | 正規化で吸収されることを見落とし |

**共通する原因は「実装前に評価方法の妥当性を確かめていない」こと。** 3 回目は advisor の指摘（「デモ表が循環論法で、b があれば直るという証拠になっていない」）で、誤った期待を bundle 側に送る直前に止められた。感度分析をしたところ `b` の精度は十分（許容 ±0.15 に対し残差 sd 0.0066）だが**胸トラップは直らない**ことが事前に分かった。

**次から実装前にやること: その効果を測る方法が、実装と同じ前提に立っているかを先に確認する。**

**追記（8/25）: 設定を変えた A/B では、まず「その設定が適用されたログ」が出力に存在するか確認する。** 数値が一致したときは「効果がない」より先に「条件が変わっていない」を疑う。4 回目の失敗はこれで防げた。

## 4. 評価基盤の欠陥を 2 つ潰した（8/25）

⑨ の差平滑化を実装したあと、`[DEPTH9]`（⑨ 適用後の値を全フレーム出すログ）を新設して効果を測った。tau=0 と tau=1.2 が**ほぼ完全一致**したため、一度は「平滑化が 1 メタフレーム内で 31 回走って収束してしまっている」と判断し、フレーム単位に間引く修正を入れた。**誤りだったので revert した。**

| # | 実際の原因 | 気付いた手がかり |
|---|---|---|
| 1 | `BatchPlaybackLogger` のガード条件に `-gapSmooth` が無く、フラグが**黙って無視**されていた。両 run とも既定 tau=1.2 で走っていた | 適用ログ `[BATCH] ... applied to N` が出力に存在しなかった |
| 2 | `& $Unity ...` は Unity を待たずに戻るため、スイープの 3 つが同時起動してプロジェクトロックを奪い合い、先行分はクラッシュしてログすら残らない | `HandleProjectAlreadyOpenInAnotherInstance` |

平滑化の実装自体は正しかった。`Time.deltaTime` は tick ごとに小さくなり 31 tick の合計が 1 メタフレームぶんになるので、進行量は tau どおりになる（tick ごとの実測: 1 フレームで +3.3mm = α 0.033、理論値 0.027）。さらに **⑧ では間引いてはいけない** — `ratio` は毎 tick 現在の姿勢から再計算されるので、この反復は「投影骨高 == bbox 高」への**不動点反復**も兼ねており、間引くと boneRatio median 0.998 が悪化する。

対処: ガード条件を撤廃（フラグを増やすたび条件に足す設計が誤り）、bool フラグは `bool?` にして未指定ならシーン値を尊重、実行は `Start-Process -Wait` で逐次化。

### ⑨ の差平滑化は有効だった

| 設定 | 全編 符号一致 | 誤差med | 1f変化 p90 | 4-8s | 36-39s |
|---|---|---|---|---|---|
| tau=0 | 83.0% | +38.2mm | 9.50mm | 38.8% | 48.1% |
| **tau=1.2（既定）** | **88.5%** | +51.6mm | **4.10mm** | 52.9% | **96.3%** |
| tau=3.0 | 87.5% | +90.5mm | 4.20mm | **60.3%** | 96.3% |

符号一致 +5.5pt、揺れ半減、36-39 秒は 48.1% → 96.3%。tau=3.0 は 4-8 秒だけ良いが全編符号一致と揺れで劣るため **tau=1.2 を維持**。（誤差 med と RMS は run ごとに再フィットする係数で正規化しており行間比較できないので、判断は符号一致と揺れに置いた。）

**⑩ の混入も確認して否定した。** `[DEPTH9]` は構造上 ⑩ の出力に不感なので「⑨ を測ったつもりが最終描画位置ではない」危険があったが、`[PENET]` を数えたところ **tau=1.2 では ⑩ が一度も発動しない**（tau=0 のときだけ 1.1% の tick で発動）。表は end-to-end で有効。

副産物として **⑩ が「効果なし」だった理由が判明した**: ⑨ の平滑化があると球がめり込む状況自体が起きず、⑩ の発動条件を満たさない。

**試算値（83.1% → 88.9%、48.1% → 96.3%）とほぼ一致した。** 今週 3 回続いた「試算と実測の食い違い」は、今回は試算ではなく**測定ハーネス側**が原因だった。
