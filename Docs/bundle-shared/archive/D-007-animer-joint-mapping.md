### 回答 `[bundle側]` 2026-08-28 — SMAL rest pose での最近傍マッチングによる対応表（実測、推測ではない）

#### 方法

AniMer が実際に読み込んでいる SMAL モデルファイル(`third_party/AniMer/data/smal/my_smpl_00781_4_all.pkl`)をそのままロードした。このファイルには 35 個の名前付き SMAL 関節の rest pose 3D 位置(`J`, 35×3)と、26 keypoint を定義する頂点グループ(`amr/models/smal_warapper.py` の `keypoint_vertices_idx`、各 keypoint はメッシュ頂点数点の平均)が両方入っている。26 keypoint 側も同じ rest pose の `v_template` から同じ頂点グループの平均を計算し、**35 関節それぞれとの 3D ユークリッド距離**で最近傍マッチングした。断定ではなく実測(推測ゼロ)。

**26 keypoint と 35 SMAL joint は別物**であることも確認しておく。`keypoints3d`/`meta.bin` の 26 点はメッシュ表面の固定頂点群の平均点であり、`body_pose` が回転を持つ 35 骨格関節そのものではない。したがって以下は「一致」ではなく「最も近い骨格関節」の対応。

#### 独立な裏付け: 既存のスケルトン辺(`ANIMER_SMAL_26_SKELETON`)と完全に整合する

`amr/utils/mesh_renderer.py`(26点可視化用)と `scripts/build_3d_pose_from_sam2.py` の `ANIMER_SMAL_26_SKELETON` は同一の 25 辺を持つ。上の対応表のラベルをそのまま当てはめると、**25 辺すべてが解剖学的に矛盾しない**(前肢: 肩→肘→手根→前足、後肢: 骨盤→膝→飛節→後足、尾: 付け根→中間→先端、顔: 鼻先端を中心に目・耳・口角が放射状、そして 7(尾の付け根)⇄18(頭) が脊椎を代表する1本の辺として肩(12/13)ともつながる)。対応が1つでもずれていれば辺の少なくとも一部が解剖学的に破綻するはずだが、そうなっていない。これは対応表の強い裏付けになる。

#### そちらの `AnimalPoseJointChains` との突き合わせ — 検証で出た2つの症状の原因が両方とも説明できる

対応表を当てはめると:

```
前肢の真の鎖(左) = 12(肩/キ甲) → 8(肘) → 14(手根) → 3(前足)
前肢の真の鎖(右) = 13(肩/キ甲) → 9(肘) → 15(手根) → 4(前足)
後肢の真の鎖(左) = 7(骨盤) → 10(膝) → 16(飛節) → 5(後足)
後肢の真の鎖(右) = 7(骨盤) → 11(膝) → 17(飛節) → 6(後足)
```

現在の `AnimalPoseJointChains`:

```
LeftFront  = { 18, 13,  9, 15 }     RightFront = { 18, 12,  8, 14 }
LeftRear   = {  7, 11, 17,  6 }     RightRear  = {  7, 10, 16,  5 }
```

**前肢**: 起点が `18`(頭)になっているが、対応表では 18 は肩(12/13)とは別の脊椎代表点で、前肢の鎖に含まれない。また `LeftFront` が使っている `13,9,15` は対応表では**右**側、`RightFront` の `12,8,14` は**左**側——**左右も入れ替わっている。** これで検証1(セグメント比が2倍ずれる: 18→13 の脊椎辺と 13→9 の本物の骨を混ぜて測っていたので比が合わない)と検証2(18→13、18→12 が剛体復元で見つからない: そもそも肩と頭は脊椎の姿勢変化で角度が変わる関係で剛体ではない)の**両方が同時に説明できる**。

**後肢**: `LeftRear={7,11,17,6}` は接続の形自体は正しい(7→11→17→6 は対応表でも実在する鎖)が、11/17/6 は対応表では**右**後肢——`LeftRear`/`RightRear` のラベルが左右で入れ替わっている。検証2で後肢が「復元骨格にある」と出たのは、鎖の**形**(どのノード同士がつながっているか)は合っていたため。

**kp12–kp13 が最も剛体的だった件**: 対応表では両方とも肩/キ甲寄りの点で、どちらも脊椎に近く体幹の姿勢とともに動く。現在の対応(左右の肘)なら剛体になるはずがないという指摘は正しいが、実体が肘ではなく肩/キ甲であれば矛盾は無い。

#### 補足: D-006 の root 定義との整合

D-006 で回答した `root_indices=[7,18]`(root = 関節7・18の中点)は、対応表では **尾の付け根(骨盤)と頭の中点** となり、体幹(脊椎)の中心を表す点として自然な選択だと分かった。D-006 の回答内容を変更する必要はないが、参考まで。

### 回答 `[bundle側]` 2026-08-28 — posed mesh で検証。交絡が原因と確定、生成経路は無矛盾

#### 方法

そちらの提案どおり、AniMer 本体のモデルコード(`third_party/AniMer/amr/models/smal_warapper.py`)と SMAL pkl(`data/smal/my_smpl_00781_4_all.pkl`)をそのまま使った。再実装はしていない。

配布した bundle の `source/keypoints3d.json` から、`pose.smal`(`globalOrient`・`pose`・`betas`、track ごとに保存済みの実パラメータ)を犬 6 フレーム・猫 6 フレーム取り出し、**2 種類の forward** に通した。

1. **`SMAL.forward()`**(そちらが使っているのと同じクラス)→ 26 keypoint(表面頂点平均、`keypoint_vertices_idx`)を出力。kp10/kp16/kp5 の位置から内角を計算
2. **`SMALLayer.forward()`**(`SMAL` の親クラス。keypoint 上書きをしないので、`lbs()` が返す**素の 35 骨格関節**がそのまま出る)→ 対応する骨格関節(LLegBack2=18 / LLegBack3=19 / LFootBack=20)の位置から同じ内角を計算

内角はそちらの数値(rest 22.9°)に合わせ、`180° − ベクトル間角度`(まっすぐ = 0°、深く曲がる = 大きい)の符号で統一した。

#### 結論: 交絡が原因。判定基準に照らすと──

そちらの判定基準どおりに読むと **posed mesh(表面頂点)の内角は 57〜69°帯**で `keypoints3d` と一致、**骨格関節だけの FK は 25〜31°帯**——**両方とも正しい計算で、指しているものが違うだけ**というのが実体。

- `keypoints3d`(=②=①)は kp10 という**表面頂点**の位置。kp10 は真の関節(LLegBack2)から **0.107m**(セグメント長 0.161m の 66%)離れている
- そちらの「SMAL FK した内角」(=③)は**関節中心そのもの**を rotate した角度で、真の骨の曲がりに近い
