## 3. bundle 側の `a`,`b` 較正値を検証

### 依頼の経緯

「ボールと人の相対位置が合わない」原因を、**Unity が `1/disparity` を距離とみなして配置している**ことと特定した。`disparity = a/Z + b` の `b` があると `1/disparity` は `Z` に比例しない。

実測（a=1.09, b=0.378）で人を 3.5m に置いたときの再現性:

| 球の実距離 | 実際の比 | Unity が再現する比 | ずれ |
|---|---|---|---|
| 3.0m | 0.857 | 0.930 | +8.5% |
| 4.5m | 1.286 | 1.112 | **−13.5%** |

これを受けて「`a`,`b` の推定値を bundle に載せてほしい」と依頼した。

### bundle 側の対応

静止した背景パッチ 2 点（近い 4.108m / 遠い 7.0m）から shot ごとに `a`,`b` を解き、`bundle_shots_depthscale_test.svb` として配布。`manifest.json` の `depth_scale_calibration` に格納（`anchor_z` は無変更）。

bundle 側は途中 2 回失敗しており（person を参照点に使うと発散、遠い点の距離を全体フィットから逆算すると負値）、その経緯も含めて報告してくれた。

### 検証結果: 較正は正しい。しかし配置は変わらなかった

**較正値の再現性:**

```
a=3.8477  b=-0.2716
person の実距離を予測 → 誤差 median +9.7%、CV 0.090
（bundle 側の報告値 0.089 と一致）
```

**独立に再現できた。** なお当方が person の全体フィットから出していた `b` は **+0.51 で符号が逆**だった。person 1 点では共線性で不安定になるという bundle 側の指摘どおり。

**配置への効果:**

| 方式 | 全編 埋もれ | 4-8s 埋もれ |
|---|---|---|
| `b` を引かない | 21.6% | **47.1%** |
| そちらの `b` = −0.2716 | 22.5% | **47.1%** |

**4-8 秒は完全に不変。**

### 原因: 依頼の前提そのものが誤っていた

利用側は配置直前に **2%/98% パーセンタイルでレンジを取り直して正規化**している。`b` は全フレーム共通の定数なので、

```
(d − b − (dMin − b)) / ((dMax − b) − (dMin − b)) = (d − dMin) / (dMax − dMin)
```

**`b` が完全に消える。** 2026-08-20 に「popout 変換の中で吸収される」と報告したのと同じ現象で、「変換の外側で引けば吸収されない」という当方の読みが誤りだった。

### 本当に必要なもの

```
現状: disparity → 2%/98% 正規化 → popout レンジへ線形配置
必要: disparity → Z = a/(disparity − b) → 実距離のまま配置（正規化しない）
```

**正規化をやめて絶対距離で配置する**という設計変更が要る。これには `a` の絶対スケールが必要だが、bundle 側も「`a` は絶対スケール不明」としている。**次週の検討事項。**

## 今週の検証手法の反省

**同じ失敗を 3 回繰り返した。** いずれも「試算では効くはず → 実装 → 実機で効かない」。

| 回 | 実装 | 誤りの所在 |
|---|---|---|
| 1 | ⑩ めり込み解消 | 試算 keypoints / 実装 実ボーン |
| 2 | ⑨ 実距離の比 | 同上 + `[PLACE]` ログで効果を測れない |
| 3 | `b` を引く依頼 | 正規化で吸収されることを見落とし |

**共通する原因は「実装前に評価方法の妥当性を確かめていない」こと。** 3 回目は advisor の指摘（「デモ表が循環論法で、b があれば直るという証拠になっていない」）で、誤った期待を bundle 側に送る直前に止められた。感度分析をしたところ `b` の精度は十分（許容 ±0.15 に対し残差 sd 0.0066）だが**胸トラップは直らない**ことが事前に分かった。

## 4. 評価基盤の欠陥を 2 つ潰した（8/25）

⑨ の差平滑化を実装したあと、`[DEPTH9]`（⑨ 適用後の値を全フレーム出すログ）を新設して効果を測った。tau=0 と tau=1.2 が**ほぼ完全一致**したため、一度は「平滑化が 1 メタフレーム内で 31 回走って収束してしまっている」と判断し、フレーム単位に間引く修正を入れた。**誤りだったので revert した。**

| # | 実際の原因 | 気付いた手がかり |
|---|---|---|
| 1 | `BatchPlaybackLogger` のガード条件に `-gapSmooth` が無く、フラグが**黙って無視**されていた。両 run とも既定 tau=1.2 で走っていた | 適用ログ `[BATCH] ... applied to N` が出力に存在しなかった |
| 2 | `& $Unity ...` は Unity を待たずに戻るため、スイープの 3 つが同時起動してプロジェクトロックを奪い合い、先行分はクラッシュしてログすら残らない | `HandleProjectAlreadyOpenInAnotherInstance` |

平滑化の実装自体は正しかった。`Time.deltaTime` は tick ごとに小さくなり 31 tick の合計が 1 メタフレームぶんになるので、進行量は tau どおりになる（tick ごとの実測: 1 フレームで +3.3mm = α 0.033、理論値 0.027）。さらに **⑧ では間引いてはいけない** — `ratio` は毎 tick 現在の姿勢から再計算されるので、この反復は「投影骨高 == bbox 高」への**不動点反復**も兼ねており、間引くと boneRatio median 0.998 が悪化する。

対処: ガード条件を撤廃（フラグを増やすたび条件に足す設計が誤り）、bool フラグは `bool?` にして未指定ならシーン値を尊重、実行は `Start-Process -Wait` で逐次化。

### ⑨ の差平滑化は有効だった

| 設定 | 全編 符号一致 | 誤差med | 1f変化 p90 | 4-8s | 36-39s |
|---|---|---|---|---|---|
| tau=0 | 83.0% | +38.2mm | 9.50mm | 38.8% | 48.1% |
| **tau=1.2（既定）** | **88.5%** | +51.6mm | **4.10mm** | 52.9% | **96.3%** |
| tau=3.0 | 87.5% | +90.5mm | 4.20mm | **60.3%** | 96.3% |

符号一致 +5.5pt、揺れ半減、36-39 秒は 48.1% → 96.3%。tau=3.0 は 4-8 秒だけ良いが全編符号一致と揺れで劣るため **tau=1.2 を維持**。（誤差 med と RMS は run ごとに再フィットする係数で正規化しており行間比較できないので、判断は符号一致と揺れに置いた。）

**⑩ の混入も確認して否定した。** `[DEPTH9]` は構造上 ⑩ の出力に不感なので「⑨ を測ったつもりが最終描画位置ではない」危険があったが、`[PENET]` を数えたところ **tau=1.2 では ⑩ が一度も発動しない**（tau=0 のときだけ 1.1% の tick で発動）。表は end-to-end で有効。

副産物として **⑩ が「効果なし」だった理由が判明した**: ⑨ の平滑化があると球がめり込む状況自体が起きず、⑩ の発動条件を満たさない。

**試算値（83.1% → 88.9%、48.1% → 96.3%）とほぼ一致した。** 今週 3 回続いた「試算と実測の食い違い」は、今回は試算ではなく**測定ハーネス側**が原因だった。

## 5. 機関車が縦向きに立っていた原因（8/28）

`bundle_train` で Else に `06_DieselLocomotive` を割り当てると機関車が**縦に立つ**。
原因は prefab ではなく**配置側**だった。

- prefab の root には X 軸 -90 度が入っており、長軸（ローカル Y、18.507m）を横へ倒している。
  **この補正は正しい**
- `TrackPlacementWriter` は `SetPositionAndRotation` で root の world 回転をまるごと書くので、
  補正が毎フレーム消える
- さらに `TrackInstanceFactory` が `Instantiate(prefab, Vector3.zero, Quaternion.identity)` で
  生成しているため、直後の `ReplaceableModel.Awake` が**補正前の姿勢**で world AABB を測る。
  高さ基準が屋根高 5.259m ではなく車体長 18.507m になり、**向きだけでなく寸法も狂っていた**

影響範囲は全 75 モデル中 2 個だけ（実測）。うち `21_Donkey1.0` の root 回転は骨の位置から
**import 由来のゴミ**と判定した（その回転は鼻〜尾の体軸を上に向ける＝ロバが尾で立つ）ので、
コードに例外を書かず prefab を正規化した。残るのは機関車 1 個。

修正後の実測: `modelH=5.2589`、縦の `sizeRatio` が median 0.988 / 0.996。
EditMode テストはベースラインと完全一致（483 passed / 25 failed、失敗リストも同一）。

### 併せて分かったこと

`bundle_train` の Else は 2 track あり、**track 0 は列車ではなく線路脇の信号柱**（22 × 132 px で
61 秒間ほぼ不変）。track 1 が列車。既定モデルが両方に入るので、信号柱の位置にも機関車が置かれている。

横方向は合わせていないため、投影幅 / bbox 幅が track 0 で median 11.4、track 1 で 0.45〜8.07 とずれる。
ただし `min(幅フィット, 高さフィット)` の自動化は**入れない**判断をした。Animal で 2026-08-07 に
否定したのと同じ壊れ方（常に縮む・採用軸が入れ替わって不連続）を train の実測でも再現するため。
幅は手動倍率＋キーフレームで合わせる方針とし、そちらを次に実装する。

## 6. ⑨ の参照点を Root → Hips に変えた（8/26）

「球が常に人より手前」という症状の原因が **モデルの `transform.position` が体の外にある**ことだと
判明した。FBX の bind pose に焼き込まれたオフセットで、⑨（人−球の深度差を追う処理）が
体の位置として使っていた点が人の中にすら無かった。

`-depthRef` で 4 種を全編実測（`bundle_human_shots_driftfix_test.svb`）:

| 参照点 | 球表面→最近傍ボーン | 球が手前の割合 | 隙間が球の直径以内 |
|---|---|---|---|
| Root（従来） | 155.2mm | 100.0% | 1.0% |
| **Hips（採用）** | **22.1mm** | 68.0% | **79.8%** |
| MeshCenter | 22.8mm | 62.6% | 76.4% |
| MeshFront | 88.8mm | 99.4% | 7.0% |

**「`anchor_z` は可視表面の depth だから MeshFront が対応するはず」という事前の読みは外れた。**
理屈で決めていたら 88.8mm で止まっていた。MeshCenter とほぼ同点だが、参照点自体の揺れが
小さい（1f 変化 1.00mm vs 1.60mm）Hips を採った。

**「ただ近づけただけ」ではない**ことも確認した。空中区間（9-12s 蹴り上げ）は 81.3mm と
離れたままで、接触すべき区間だけ 20〜27mm に寄る。接触判定もしきい値も入れていない。

**副作用の解消**: Hips 参照で移動量が 43.1mm → 163.7mm に増え、球が bbox より小さく写るように
なった。深度を動かしたらスケールも追従させる（`matchOtherScaleToFollowedDepth`、既定 true）。
投影半径 / bbox 半径が **0.820 → 1.001**。実機で「だいぶ良くなった」と確認済み。

**確定した教訓**: `instance.transform.position` は「人がいる場所」ではない。深度を扱うコードが
これを人の位置として使ってはいけない。

## 8. Animal の姿勢一致を初めて測った（8/27〜8/28）

### 指標を作ったら、指標が乗っている前提が未検証だった

`[ANIMALKP]`（ボーンと keypoints3d の角度差）を新設したところ human とは桁が違った。
しかし **AniMer 26 関節と Unity ボーンの対応づけ自体が一度も検証されていない**ことに気付き、
数値を解釈できない状態になった。セグメント長比で照合したところ **対応づけが検証に落ちた**ので
一度撤回し、bundle 側に解剖学的な対応表を依頼した（D-007）。

回答は **SMAL rest pose での最近傍マッチングによる実測**（推測ではない）で届いた。
こちらで独立検証を通して受け入れた:

| 検証 | 結果 |
|---|---|
| 左右を入れ替えた対立候補との長さ比較 | **10/10 で主張するリンクのほうが短い** |
| 前肢の 1:2 長さ比 | 通った |
| 2:3 長さ比 | 通らなかったが、**こちらの判定基準のほうが誤り**だった |

**D-007 は解決。** 併せて bundle 側が posed mesh 由来の keypoint が配布物の `keypoints3d` と

### 指標に下駄が乗っていた

## 6. Else の手動スケール（8/28）

「回転したあとに大きさを合わせ直したい」「二つの frame でそれぞれ調整したら間が遷移してほしい」
への対応。自動で幅も合わせる案（`min(幅フィット, 高さフィット)`）は実測で否定したうえで、
**手動倍率＋キーフレーム**にした。

- 最終スケール = 自動フィット（bbox 高さ合わせ）× 手動倍率。絶対値ではなく倍率にしたのは、
  自動フィットが depth と bbox から毎フレーム動くため
- 補間は yaw と同じ実装を `TrackKeyframeCurve` に切り出して共有
- 永続化は `model_selection.json` の `"scale"`。`operations.csv` に `change_scale` を記録

### 手動倍率を入れて初めて表面化した欠陥 2 件

どちらも Human / Animal 専用の「測り直し」経路で、Else には効かない。

- **⑧ 深度の測り直し**が、ユーザーが 2 倍にしたぶんだけモデルを**奥へ押しやって打ち消していた**。
  倍率を割り戻すよう直した。倍率 1.0 と 2.0 のどちらでも最終深度が 0.7667 に収束することを実測
- **⑨ ロック済みスケールの測り直し**は割り戻しても合わなかった。投影高はスケールに厳密には
  比例せず（モデルは眼から 0.44〜0.77m と近い）、×2 のとき補正が ×0.934 と逆向きに効いて
  スライダーの 2.00 が 1.55 倍にしかならなかった。この補正の目的は「自動フィットを bbox に
  合わせる」ことで、手動倍率はわざとそこからずらす指定なので、**倍率が 1.0 でない track では
  丸ごと止める**ことにした

### 実測

| 条件 | userScale | sizeRatio |
|---|---|---|
| Else 倍率なし | 1.0000 | 0.997 |
| Else ×2 | 2.0000 | **1.983** |
| Person ×2 | 2.0000 | 1.582（モデルのスケールは 1.954 倍。遠近のぶん見かけが縮む） |

キーフレーム間の遷移も実測で完全な線形（f=0 で 1.0、f=900 で 3.0 を打って
f=300 が 1.6667、f=600 が 2.3333）。track ごとに独立していることも確認。

### Editor で確認できるようにした

実機の VR UI を触らないと確認できなかった操作を、batchmode から注入できるようにした。

- `-manualYaw "track:deg"` / `-manualScale "track:frame:値"` … 手動調整の注入
- `-openSettings true` … 設定パネルを開いた状態で始める（パネルの配置は目で見るしかない）
- `-captureFrames` は元からあるので、そのままレンダリング画像が撮れる

Settings パネルは行が 1 つ増えたので canvas を 900x520 → 900x640 に組み直した。
